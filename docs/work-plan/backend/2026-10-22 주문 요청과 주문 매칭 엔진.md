# 주문 요청과 주문 매칭 엔진

- 작업 날짜: 2026-10-22
- 작업 영역: backend
- 관련 계획: 해당 없음. 별도의 에이전트 실행용 구현 계획은 작성되지 않았다.

## 4. 동작 구조

### 개요

#### 주문 요청과 저장

1. 로컬 개발 환경에 테스트용 `member`, `account`, `stock` 데이터를 준비한다. 주문 요청 시 회원과 계좌를 새로 생성하지 않는다.
2. 클라이언트가 매수 또는 매도 요청과 `memberId` 헤더를 전송한다. API 경로는 `/v1/order/buy`, `/v1/order/sell`을 기준으로 한다.
3. `local` 프로필의 `LocalAuthWebMvcConfig`가 등록한 `HeaderMemberIdArgumentResolver`가 헤더 문자열을 `Long`으로 변환하여 `@CurrentMemberId Long memberId` 인자에 주입한다. 누락·공백과 숫자 변환 실패는 요청 오류로 처리한다. 
4. 컨트롤러는 주문 요청과 현재 회원 ID를 `OrderService`에 전달한다. 요청 본문에서 별도의 회원 ID나 계좌 ID를 받지 않는다.
5. 서비스는 `memberId`로 `account`를 조회하고, 요청의 종목 코드로 `stock`을 조회한다. 회원의 다른 정보가 필요하지 않다면 선행 `member` 조회는 하지 않는다.
6. 요청 본문은 `@Validated`로 검증한다. 요청 경로로 BUY/SELL을 구분하여 `Order`를 생성하고 신규 상태는 생성 시 `ACCEPTED`로 통일한다. 시장가 가격 생략을 지원하는 조건부 검증은 별도 정책 확인 대상으로 둔다.
7. 계좌와 종목을 연결한 주문을 트랜잭션 안에서 저장하고 성공 응답을 반환한다. 이 응답은 주문 접수·저장 성공을 뜻하며 체결 완료를 뜻하지 않는다. Task 1에서는 호가장 등록과 매칭 실행을 포함하지 않는다.

#### 주문 매칭 엔진

1. 저장된 신규 주문을 엔진 입력으로 연결한다. 직접 호출, 이벤트 등 구체적인 호출 방식은 미정이며 Task 2에서 확정한다.
2. `order_book`으로 상대 주문 후보를 탐색한다. 
3. 확정한 매칭 정책에 따라 상대 주문을 선택하고 매칭 가격·수량 및 잔여 수량을 계산한다. 가격 우선·시간 우선은 구조도에 제시된 후보 규칙이며, 이번 계획에서는 확정하지 않는다.
4. 매칭 없음, 부분 매칭, 전량 매칭을 구분할 수 있는 결과를 반환한다. 여러 상대 주문 탐색의 반복·종료 조건은 매칭 정책을 정할 때 함께 정의한다.
5. 이번 범위의 종점은 매칭 결과 생성이다. `execution` 저장, 주문 상태 변경 등 체결 결과 영속 반영은 이후 체결 처리 작업에서 다룬다. 호가장 등록·갱신·제거와 영속 반영 사이의 책임 및 트랜잭션 경계는 연계 계약으로 정리하고 임의로 확정하지 않는다.

### 동작 구조를 선택한 이유

- 현재 회원 식별을 `@CurrentMemberId` 뒤로 분리하여, 헤더 기반 개발용 식별을 Security 인증 정보로 바꾸더라도 컨트롤러와 주문 서비스의 호출 구조를 유지한다. 헤더 값은 인증 증명이 아니므로 로컬 개발에 한정한다.
- 계좌 조회를 주문 서비스에 두어 주문 생성에 필요한 계좌를 업무 처리 안에서 결정한다. 저장 이후에는 `orders.account_id`를 사용하므로 체결·결제에서 최초 요청자의 인증 정보를 다시 요구하지 않는다.
- 주문 저장과 매칭 계산을 단계적으로 구현하여, DB 저장 문제와 상대 주문 선택·수량 계산 문제를 분리해서 검증한다.
- 매칭 결과 생성과 체결 결과 반영을 분리하여, 아직 구현하지 않는 체결·결제 기능 없이 엔진의 입력과 결과를 검증한다. 단, 계산 결과만으로 실제 체결이 완료된 것으로 취급하지 않는다.
- 주문 테이블은 `orders`, ID 컬럼은 `order_id`로 사용한다. `side`는 `VARCHAR(4)`, `type`은 `VARCHAR(6)`에 enum 이름을 저장하여 엔티티의 문자열 매핑과 일치시킨다.
- SQL에는 `orders.remaining_quantity`가 없고 `order_book.remaining_quantity`가 있다. 앞선 대화의 추가 제안만으로 컬럼 변경을 확정하지 않으며, 수량 원본과 동기화 책임은 Task 2 설계 시 확인한다.

## 6. 단계별 작업 내용

### Task 1. 주문 요청을 받아 DB에 저장

- 목적: 인증 구현에 종속되지 않는 회원 식별 경계를 두고, 매수·매도 요청을 계좌와 종목에 연결해 저장한다.
- 작업 내용:
  - `@CurrentMemberId`와 개발용 resolver를 사용하고 `local` 프로필에서 헤더를 `Long`으로 변환·주입한다. 회원 ID 타입은 컨트롤러·서비스·계좌 조회 repository에서 동일하게 사용한다.
  - 컨트롤러 기본 경로는 `@RequestMapping("/v1/order")`로 매핑하고 매수·매도 요청을 각각 `/buy`, `/sell`로 받는다.
  - 서비스에서 회원 ID로 계좌를 조회하고 종목 코드로 종목을 조회한다. 없는 계좌·종목 및 잘못된 입력의 실패 응답을 정의한다.
  - Validation starter를 사용하여 요청 본문에 `@Validated`를 적용한다. 종목 코드는 `@NotBlank`, `Integer type`은 `@NotNull`·`@Min(0)`·`@Max(1)`, 가격과 수량은 `@NotNull`·`@Positive`로 검증하고 항목별 메시지를 지정한다. 시장가 가격 생략 여부는 별도 정책 확인 대상으로 남긴다.
  - 신규 주문은 `ACCEPTED` 상태로 생성하고 계좌·종목·방향·유형·가격·수량·시간을 저장한다. 실패 시 주문이 저장되지 않도록 트랜잭션 경계를 검증한다.
  - SQL과 엔티티의 테이블명은 `orders`, PK 컬럼은 `order_id`로 통일한다. `side`는 `VARCHAR(4)`의 BUY/SELL, `type`은 `VARCHAR(6)`의 LIMIT/MARKET으로 저장하며 관련 FK 참조·주석·CHECK 제약도 같은 정의를 따른다. 실제 DB 스키마와의 일치는 실행 검증으로 확인한다.
  - 계좌 주문 가능 금액·보유 수량 검증 및 예약은 구조도에 제시되어 있으나 세부 정책이 미정이다. 단순 접수·저장의 검증과 실제 주문 가능 여부 보장을 구분하고, 이번 Task에 포함할 수준을 구현 전에 확인한다. 체결·계좌 반영까지 확장하지 않는다.

### Task 2. 주문 매칭 엔진 구현

- 목적: 신규 주문과 상대 주문을 비교하여 후속 체결 처리에 전달할 매칭 결과를 만든다.
- 작업 내용:
  - Task 1의 저장된 주문을 기준으로 엔진 입력과 호출 시점을 정의한다.
  - `order_book`을 이용한 상대 주문 탐색 책임과 신규 주문의 호가장 등록 시점을 정한다.
  - 매칭 우선순위는 **미정**으로 둔다. 여러 가격·동일 가격·서로 다른 접수 시각의 주문 사례를 작성하고, 기대하는 선택 순서를 사용자와 확인한 뒤 확정한다.
  - 체결 가격 결정, 주문 유형별 지원 범위와 잔량 처리, 반복 탐색·종료 조건도 같은 방식으로 확정한다.
  - 결과에는 양쪽 주문 식별자, 매칭 가격·수량 및 잔여 수량 등 후속 처리에 필요한 정보를 정의한다. DTO 이름과 세부 구조는 엔진 책임과 체결 처리 경계를 확인한 후 정한다.
  - 매칭 없음, 부분 매칭, 전량 매칭과 여러 상대 주문에 대한 계산을 검증한다. 같은 상대 주문을 중복 선택하지 않기 위한 실행 직렬화·잠금 등 동시성 방식은 실행 구조를 정할 때 함께 검토한다.
  - 호가장 변경과 후속 체결 저장 실패 시 정합성 경계를 문서화하되, 체결 처리 모듈과 결제 기능은 구현하지 않는다.

| DB 매핑 | 실제 테스트 DB 정의와 엔티티 대조 및 JPA validate | 테이블명과 enum·컬럼 형식이 일치하여 저장·조회가 가능하다. |
| 매칭 없음·부분·전량 및 여러 상대 주문 | Task 2 정책 확정 후 입력과 기대 결과를 고정한 엔진 단위 테스트 | 정책에 맞는 상대 주문과 가격·수량을 반환하고 음수 잔량·중복 수량 계산이 없다. |
| 매칭 우선순위 | 정책 확정 후 가격·접수 순서가 다른 사례 테스트 | 확정한 우선순위와 반복·종료 조건대로 결과가 생성된다. 현재는 기대 순서를 확정하지 않는다. |
| 범위 경계 | 엔진 테스트에서 체결 저장·결제 처리 호출 여부 확인 | 결과 생성까지 수행하고 `execution`·`settlement` 저장이나 체결 이벤트 발행을 수행하지 않는다. |
