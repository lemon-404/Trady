# 토큰 발급 갱신 폐기 정책 검증

- 작성 날짜: 2026-10-10
- 검증 대상: 같은 앱키의 접근 토큰 발급·재발급·폐기 정책
- 실제 API 검증: 사용자 수동 확인 내용과 자동 테스트 실행 결과를 구분하여 아래 기록

## 1. 확인 목적

같은 앱키를 사용하는 수집 프로세스들이 토큰을 각각 관리할 수 있는지 확인한다. 재발급이 기존 토큰에 미치는 영향과 정상 종료 시 폐기 범위를 확인하여 운영 중 갱신·종료 정책을 결정한다.

## 2. 공식 자료와 확인 경로

## 3. 테스트 방법

- 테스트 코드: [KiwoomTokenIssueRenewalRevocationPolicyTest.java](<../../../../backend/src/test/java/trady/com/backend/global/dataloader/kiwoom/auth/KiwoomTokenIssueRenewalRevocationPolicyTest.java>)

### 실행 방법

- 토큰 정책 확인이 필요할 때 개별 테스트 메서드를 실행하여 확인한다.
- `kiwoom-token` 태그는 Gradle 기본 test 작업에서 제외된다. 개별 실행은 IDE의 JUnit 직접 실행을 사용한다.

### 주의 사항

- 설정 파일에 키움 인증 설정이 필요하다.
- 실제 키움 모의투자 API를 호출하므로 같은 인증정보를 사용하는 다른 프로세스의 호출을 중단한 상태에서 실행한다.
- 현재 요청 간격 제어와 자동 재시도가 없어 연속 요청에서 429가 발생할 수 있다. 요청 제한·통신 장애·일반 업무 오류는 인증 거절로 판단하지 않는다.

## 4. 검증 결과

### 1. 발급 토큰의 사용

| 구분 | 내용 |
|---|---|
| 검증 방법 | 발급받은 토큰으로 종목정보를 조회하고, 발급된 토큰의 유효기간이 남아 있는지 확인 (`issuedTokenCanQueryStock`) |
| 예상 결과 | 종목정보 조회 성공 및 토큰의 유효기간이 남아 있음 |
| 실제 결과 | 사용자가 발급 토큰으로 실제 사용을 확인함 |

발급 토큰을 실제 요청에 사용할 수 있음을 확인했다. Auth Client의 발급 결과를 검증한 뒤 토큰 제공에 사용한다.

### 2. 짧은 간격 재요청

| 구분 | 내용 |
|---|---|
| 검증 방법 | 같은 앱키로 발급 API를 두 번 호출하여 토큰과 만료 시각을 비교 (`immediateReissueReturnsSameToken`) |
| 예상 결과 | 동일한 토큰과 만료 시각 반환 |
| 실제 결과 | 개별 테스트 메서드 실행으로 동일한 토큰과 만료 시각이 반환되는 것을 확인함 |

짧은 간격으로 재요청해도 동일한 토큰과 만료 시각이 반환되므로, 요청마다 독립적인 토큰이 생긴다고 가정하지 않고 같은 앱키의 토큰 관리 주체를 조율한다.

### 3. 6시간 이후 재요청

| 구분 | 내용 |
|---|---|
| 검증 방법 | 실제 요청 실험 대신 공식 토큰 안내 확인 |
| 예상 결과 | 6시간 이후 재요청 시 새 토큰 발급 및 기존 토큰 폐기 |
| 실제 결과 | 실험 미수행 |

공식 교체 정책을 근거로 갱신을 설계한다. 기존 토큰의 별도 원격 폐기는 바로 추가하지 않는다.

### 4. 재발급 후 이전 토큰

| 구분 | 내용 |
|---|---|
| 검증 방법 | 실제 요청 실험 대신 공식 안내의 기존 토큰 폐기 정책 확인 |
| 예상 결과 | 교체된 이전 토큰으로 요청하면 인증 거절 |
| 실제 결과 | 실험 미수행 |

공식 안내를 근거로 갱신 시 제공할 토큰을 새 토큰으로 교체하며, 같은 앱키를 사용하는 프로세스에 미치는 영향을 고려한다.

### 5. 명시적 폐기

| 구분 | 내용 |
|---|---|
| 검증 방법 | 종목 조회 성공 → 토큰 폐기 → 같은 토큰으로 재조회 (`revokedTokenCannotQueryStock`) |
| 예상 결과 | 토큰 폐기 성공 및 폐기한 토큰의 재조회 시 인증 거절 |
| 실제 결과 | 기존 클래스명 KiwoomTokenPolicyLiveTest의 개별 실행 성공 기록 확인. |

명시적 폐기 후 인증 거절을 확인했으므로, 폐기한 토큰을 이후 요청에 제공하지 않도록 관리한다.

### 6. 복수 토큰 간 폐기 영향

| 구분 | 내용 |
|---|---|
| 검증 방법 | 공식 안내에 따라 독립적인 복수 토큰을 유지하는 실험은 검증 범위에서 제외 |
| 예상 결과 | 같은 앱키의 발급 요청마다 독립적인 토큰이 생기지 않을 수 있음 |
| 실제 결과 | 실험 미수행 |

공식 안내상 같은 앱키의 토큰이 반환되거나 교체되므로, 프로세스별 발급·폐기가 서로 독립적이라고 가정하지 않는다. 여러 토큰 사이의 폐기 영향은 실험으로 확인하지 않았다.
