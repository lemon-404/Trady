| 동기화 실행 | application.properties의 candle.sync-setup과 Runner로 서버 시작 시 선택적으로 한 번 실행 |

## 4. 동작 구조

### 개요

**종목·캔들 동기화**

~~~text
서버 시작
→ candle.sync-setup=true인 경우 Runner 실행
→ 토큰 준비 후 선택한 종목 정보 조회·DB 적재
→ 해당 종목의 과거 캔들 REST 조회·DB 적재
→ 동기화 종료 후 서버 유지
~~~

candle.sync-setup의 기본값은 false로 둔다. true일 때 ApplicationRunner를 @ConditionalOnProperty로 등록하여 부팅마다 한 번 동기화한다. false이거나 설정이 없으면 동기화하지 않는다. 별도 프로필이나 실행 모드는 추가하지 않는다. Runner는 종목 정보와 캔들 수집 서비스를 순서대로 호출하며, 사용자가 필요할 때 같은 동기화 기능을 다시 실행할 수 있도록 수집 로직과 시작 코드를 구분한다.

종목 정보는 KiwoomStockClient.getStockList()로 ka10099의 목록을 조회하고, 응답의 시장 구분과 선택한 종목 코드로 적재 대상을 골라 stock에 저장한다. 캔들은 KiwoomStockCandleClient의 REST 요청과 필요한 연속 조회로 가져와 변환·검증한 뒤 stock_candle에 저장한다. 기존 Candle 엔티티와 테이블의 매핑을 확인하고 종목·봉 주기·봉 시각을 기준으로 저장한다. 이미 저장된 캔들은 갱신하고 새로운 캔들은 추가한다. 진행 중인 봉의 식별 방법은 차트 API 응답을 확인해 정하고, 이번 과거 적재에는 완성된 봉을 사용한다.

API 스펙 확인은 공식 안내의 국내·미국 공통 모의투자 호출 제한을 기준으로 KiwoomStockCandleClientTest에서 초당 1회와 초당 2회 요청을 비교한다. 초당 2회는 공식 허용값이 아니라 요청 제한의 동작을 확인하기 위한 실험 조건이다. 실제 모의투자 차트 적재에서는 같은 토큰·같은 차트 TR의 요청을 종목과 페이지에 걸쳐 합산하여 초당 1회로 제어한다. 종목별로 각각 초당 1회씩 보내지 않는다. 응답 오류를 정상 데이터로 저장하지 않으며 자동 재시도와 복구는 후속 과제로 둔다.

**차트 조회**

~~~text
사용자 차트 요청
→ ChartController
→ ChartQueryService
→ DB의 캔들 조회
→ 응답
~~~

사용자 요청은 키움 API나 동기화를 실행하지 않는다. 조회는 선택한 종목의 DB 적재 범위 안에서 제공하며, 상세 요청 조건과 응답 형식은 기존 API 설계와 적재 데이터를 바탕으로 Task 3에서 정한다.

### 동작 구조를 선택한 이유

| 책임 | 이유 |
|---|---|
| API 확인과 적재 구현 | 실제 요청·응답 규격을 확인한 뒤 저장 로직을 작성 |
| 종목 정보와 캔들 적재 | 종목 정보를 먼저 준비하여 캔들이 참조할 종목을 확보 |
| 수집 서비스와 Runner | 같은 수집 기능을 최초 적재와 필요 시 동기화에 재사용 |
| 수집과 사용자 조회 | 사용자 수와 조회 여부에 관계없이 데이터를 준비하고, 조회에서 외부 API 호출 제거 |
| 과거 수집과 실시간 수집 | 이후 실시간 데이터를 추가하더라도 사용자 요청의 DB 조회 구조 유지 |

## 6. 단계별 작업 내용

### Task 1. KiwoomStockCandleClient로 API 스펙 확인

- 목적: 종목·캔들 적재에 적용할 공통 호출 제한과 분봉 데이터 기준을 정한다.
- 작업 내용: 키움 공식 소개의 국내·미국 공통 적용사항 중 모의투자 계좌별·토큰별·TR별 초당 1회 제한을 기준으로 삼는다. KiwoomStockCandleClientTest에서 단건 응답 시간을 측정하고, 초당 1회 요청과 초당 2회 요청 시 동작을 비교한다.
- 작업 내용: KiwoomStockCandleClient.getKiwoomStockCandle()로 ka10080의 1분·5분·15분봉을 조회하여 응답 목록 개수, 봉 시각과 거래 시간대의 데이터를 확인한다. 최대 1년 제공 안내는 ka10080에만 적용한다.
- 작업 내용: 실제 결과와 KiwoomStockClient 대신 Candle Client로 검증한 이유는 수행 기록에 남긴다. 다음 단계는 이 기준에 따른 적재 구현이며, 별도 Task에서 API 스펙 확인을 반복하지 않는다.

### Task 2. 종목 N개와 해당 종목의 캔들 DB 적재 구현

- 목적: 사용자에게 제공할 종목 정보와 과거 캔들을 DB에 준비한다.
- 작업 내용: 제공할 종목 N개를 선택한다. KiwoomStockClient.getStockList()의 ka10099 목록에서 해당 종목의 코드·이름·시장 정보를 골라 Stock 엔티티에 맞춰 저장한다. 기존 종목은 같은 식별 관계를 유지하며 정보를 갱신하고 새 종목은 추가한다.
- 작업 내용: Task 1의 기준으로 수집 기간을 정하고 KiwoomStockCandleClient로 각 종목의 1분·5분·15분봉을 조회한다. 과거 기간 수집에 필요한 연속 조회는 이 단계에서 연결한다. 같은 토큰·같은 TR의 요청을 종목과 페이지에 걸쳐 초당 1회로 제어한다.
- 작업 내용: OHLCV와 봉 시각을 Candle 엔티티에 맞춰 검증·저장한다. 동일한 종목·봉 주기·봉 시각은 갱신하고 새로운 캔들은 추가한다. 적재 결과를 응답과 비교하고 재실행 시 중복 여부를 확인한다.
- 작업 내용: application.properties에 candle.sync-setup=false를 기본값으로 두고 Runner에 @ConditionalOnProperty(name = "candle.sync-setup", havingValue = "true")를 적용한다. 토큰 준비 후 종목 적재 → 캔들 적재를 한 번 실행하며 서버는 유지한다. 설정이 false이거나 없으면 동기화하지 않는다.

### Task 3. 1분·5분·15분봉 DB 조회 API 구현

- 목적: 사용자에게 외부 API 호출 없이 저장된 차트 데이터를 제공한다.
- 작업 내용: 종목 코드·봉 주기·조회 기간으로 DB의 1분·5분·15분봉을 조회하는 Controller·Service·응답 객체를 구현한다. 세부 URI·조회 개수·정렬·오류 응답은 기존 API 설계와 제공 범위를 기준으로 정한다.
- 작업 내용: 저장된 OHLCV와 봉 시각을 응답한다. 빈 구간을 조회해도 키움 호출이나 자동 수집을 실행하지 않는다. 조회 결과가 DB 내용과 일치하며 외부 호출이 없는지 확인한다.
