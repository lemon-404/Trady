## 4. 동작 구조

### 개요

**시작:** Token Lifecycle → Token Provider → Auth Client → Kiwoom REST API 순서로 토큰을 준비한다. 발급 응답의 성공 여부, 토큰과 만료 시각을 검증한 뒤 Access Token으로 보관한다. 초기화 실패는 시작 경로로 전달한다.

**사용:** 요청 측은 주입받은 Token Provider의 토큰 제공 경로를 사용한다. Provider는 현재 토큰의 남은 유효기간을 확인하고, 만료까지 1분보다 많이 남아 있으면 보관 토큰을 제공한다. 토큰이 없으면 발급하고, 만료까지 1분 이하로 남아 있으면 갱신한 뒤 제공한다. 1분은 기존 구현의 여유 시간이며 외부 요청 완료를 보장하는 값은 아니다. 외부 객체가 private token 필드에 직접 접근하지 않고, 읽는 경로도 같은 동기화 경계로 연결한다.

**갱신:** Token Provider의 renewalToken() → Auth Client → Kiwoom REST API로 연결한다. 갱신 필요 여부를 판단하는 과정과 실제 갱신을 수행하는 과정은 구분한다. renewalToken()은 호출할 때 갱신을 수행하며, 요청마다 무조건 호출하지 않는다. 토큰이 없는 상태의 초기 발급은 초기화·토큰 제공 경로가 담당한다.

생성 시점부터 정확히 24시간 뒤에 만료된다는 전제로, 남은 유효기간은 expire - now로 계산한다. 발급 요청 시각을 생성 시각으로 따로 기록하지 않고 응답의 만료 시각을 사용한다.

| 남은 유효기간 | 판단 | 갱신 동작 |
|---|---|---|
| 18시간 초과 | 생성 후 6시간 이전 | 현재 토큰 폐기 → 발급 응답 검증 → 새 토큰과 만료 시각 보관 |
| 18시간 이하 | 생성 후 6시간 경과 | 발급 응답 검증 → 새 토큰과 만료 시각으로 교체. 기존 토큰의 별도 폐기 요청 없음 |

18시간 경계는 이번 구현의 분기 기준으로 다룬다. 매 요청의 만료 확인만으로 갱신할 때는 만료가 가까운 경우에 실행되며, 6시간 이전 분기는 유효 토큰의 갱신을 명시적으로 요청하는 경우를 지원한다. 6시간마다 무조건 갱신하는 주기 정책을 의미하지 않는다.

폐기가 실패하면 후속 발급을 진행하지 않고 실패를 전달한다. 폐기 성공 후에는 이전 보관 값을 제거하므로 이후 발급이 실패해도 폐기된 토큰을 제공하지 않는다. 발급 응답을 검증한 뒤 반드시 보관 값에 반영한다. 발급·검증 실패 시에는 실패를 전달하고 이전 토큰이 계속 유효하다고 임의로 판단하지 않는다.

**정상 종료:** Token Lifecycle → Token Provider → Auth Client → Kiwoom REST API로 현재 토큰을 폐기한다. 종료 경로는 새로운 토큰 제공과 갱신을 차단하고 진행 중인 토큰 관리 작업과 순서를 맞춘 뒤 폐기한다. 운영 중 갱신을 위한 폐기는 종료 상태로 전환하지 않는다. 원격 폐기의 성공·실패를 구분하여 기록하고, 실패를 폐기 완료로 표현하지 않는다. 강제 종료에서는 원격 폐기를 보장하지 않는다.

토큰 제공·갱신·폐기는 같은 Provider 객체의 잠금으로 관리한다. synchronized 메서드 내부에서 호출한 private 발급 메서드도 잠금을 유지한 상태에서 실행된다. 이 보호는 동일한 Provider 객체를 사용하는 스레드 사이에 적용되며, 다른 프로세스나 토큰 제공 이후의 실제 API 요청까지 보호하지 않는다. 수집 작업 전체의 종료 순서와 프로세스 잠금은 관련 종목·차트 수집 계획에서 연결한다.

### 동작 구조를 선택한 이유

| 책임 분리 | 기대하는 효과 |
|---|---|
| 시작·종료 연결과 토큰 갱신 | 기존 Lifecycle을 유지하면서 실행 중 필요한 갱신을 Provider에서 처리 |
| 갱신 조건과 갱신 실행 | 정상 토큰을 재사용하고, 필요한 경우에만 갱신하여 매 요청의 불필요한 발급 방지 |
| 토큰 관리와 외부 인증 통신 | 갱신 정책은 Provider에서, 키움 요청·응답 처리는 Auth Client에서 변경 |
| 운영 중 폐기와 종료 처리 | 갱신 과정의 폐기로 Provider가 종료 상태에 들어가는 문제 방지 |
| 갱신과 요청 복구 | 토큰 교체를 먼저 구현하고, 인증 오류 후 재요청은 추후 공통 계층에서 처리 |

## 6. 단계별 작업 내용

### Task 1. 토큰 발급·갱신·폐기 정책 검증

- 목적: 토큰이 키움 API에서 어떻게 다뤄지는지 확인하여 갱신 정책의 근거를 확보한다.
- 작업 내용: 발급 토큰 사용, 짧은 간격 재요청 시 토큰·만료 시각 유지, 명시적 폐기를 개별 테스트 메서드로 확인한다. 생성 후 6시간 이후의 교체 정책은 공식 안내를 근거로 삼고 실제 실험과 구분한다.
- 작업 내용: 실제 결과와 그에 따른 결정은 토큰 발급 갱신 폐기 정책 검증 수행 기록에 남기고, 이 계획에는 구현에 적용할 기준만 정의한다.

### Task 2. Provider 갱신 기능과 Lifecycle 연결 구현

- 목적: 프로토타입에서 요청 시 필요한 갱신을 지원하면서 시작·종료 동작을 유지한다.
- 작업 내용: 초기 발급, 보관 토큰 제공, 갱신 수행의 역할을 구분한다. 요청마다 남은 유효기간을 확인하고 정상 토큰은 재사용하며, 필요한 경우에만 갱신한다.
- 작업 내용: renewalToken()은 now에서 expire까지의 남은 시간을 계산한다. 18시간 초과면 폐기 후 발급하고, 18시간 이하면 발급 후 교체한다. 발급 응답의 검증 결과를 보관 값에 반영한다.
- 작업 내용: 폐기 성공 시 보관 값을 무효화하고, 실패 시 다음 발급으로 넘어가지 않는다. 발급·응답 검증 실패를 전달하며 사용할 수 없는 토큰을 제공하지 않는다.
- 작업 내용: 토큰 읽기·갱신·폐기를 같은 동기화 경계로 연결한다. 운영 중 갱신용 폐기와 종료 상태 전환을 분리하고, 종료 후 새 발급을 막는다. Lifecycle의 시작 시 초기화·종료 시 폐기 역할은 유지하며 실패 후 폐기 완료 로그가 나오지 않도록 한다.
