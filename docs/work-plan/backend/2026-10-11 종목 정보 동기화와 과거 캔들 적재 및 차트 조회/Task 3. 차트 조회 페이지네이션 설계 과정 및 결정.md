## 3. 검토 과정

### 1. 페이지네이션 기법 비교

| 기법 | 동작 방식 | 검토 내용 |
|---|---|---|
| Offset Pagination | 지정한 개수의 행을 건너뛰고 다음 목록 조회 | 구현은 간단하지만 깊은 과거로 이동할수록 건너뛰는 데이터 증가 |
| Keyset Pagination | 마지막 데이터의 정렬 기준값으로 다음 범위 조회 | 종목·봉 주기·시각을 기준으로 과거 범위를 조회하고 인덱스 활용 가능 |
| Cursor Pagination | 다음 조회 위치를 응답에 담아 클라이언트가 후속 요청에 전달 | 스크롤 기반 연속 조회에 필요한 위치 전달에 적합 |

페이지 번호로 이동하는 Offset 대신 시각을 기준으로 이어 조회한다. Keyset은 DB의 조회 방식이며 Cursor는 API에서 다음 조회 위치를 전달하는 방식이므로 함께 적용한다. 시각 커서를 전달하는 Keyset 기반 페이지네이션으로 구성한다.

### 2. 스크롤 중 데이터 로딩

처음에는 화면에 필요한 양보다 많은 데이터를 최초 요청에 담아 미리 확보하는 방식을 고려했다. 화면에 100개가 필요할 때 500개를 받아 보관하는 방식이다.

이후 확보한 과거 데이터가 소진되기 전에 다음 페이지를 비동기로 요청하는 Prefetch 방식으로 정했다. 최초 조회량을 크게 늘리는 대신 남은 캔들 개수에 따라 추가 요청한다. 최초 조회량과 추가 조회량은 동일한 서버 고정 LIMIT을 사용한다.

### 3. 키움 연속 조회와 직렬화 커서 검토

키움 REST API는 최초 요청에 cont-yn: N을 사용하고, 연속 요청에는 cont-yn: Y와 응답의 next-key를 전달한다. 클라이언트가 응답받은 다음 위치를 후속 요청에 전달하는 흐름을 자체 API에도 적용한다. 키움의 헤더와 Trady의 요청·응답 필드는 별개이며, 사용자 조회에서 키움 next-key를 사용하지 않는다.

키움의 next-key가 종목·봉 주기·조회 시각 등을 직렬화한 Stateless Cursor일 가능성을 검토했다. 키움의 내부 구현이 실제로 이 방식인지는 확인되지 않았으며, 연속 조회 인터페이스를 보고 도출한 분석이다.

Trady에도 조회 조건을 하나의 직렬화 토큰에 담으면 클라이언트의 내부 조회 조건 관리 부담을 줄이고, 별도의 커서 매핑 테이블 없이 조건을 복원할 수 있다. 다만 포함 데이터, 인코딩, 무결성 검증과 버전 관리가 필요하다. 프로토타입에서는 명시적인 종목·봉 주기·시각을 사용하고 직렬화 토큰은 후속 과제로 둔다.

## 4. 요청·응답 구조와 조회 정책

### 1. Request

POST 요청의 JSON 본문으로 stockCode·interval·cursor를 받는다. 최초·연속 조회는 HTTP 헤더 cont-yn으로 구분한다. Controller의 @PostMapping(headers = "cont-yn=N")과 @PostMapping(headers = "cont-yn=Y")가 각각 최초·연속 메서드를 선택하므로 Service 호출을 조건문으로 분기하지 않는다.

| 위치 | 필드 | 설명 |
|---|---|---|
| 헤더 | cont-yn | N은 최초 요청, Y는 연속 요청 |
| JSON 본문 | stockCode | 조회할 종목 코드 |
| JSON 본문 | interval | 봉 주기: 1·5·15 |
| JSON 본문 | cursor | 최초 요청에서는 기준 시각, 연속 요청에서는 이전 응답의 nextCursor |

최초 요청 헤더는 cont-yn: N이며 본문은 다음과 같다.

~~~json
{
  "stockCode": "005930",
  "interval": "1",
  "cursor": "2026-10-09T15:00:00"
}
~~~

연속 요청 헤더는 cont-yn: Y이며 본문은 다음과 같다.

~~~json
{
  "stockCode": "005930",
  "interval": "1",
  "cursor": "2026-10-09T14:58:00"
}
~~~

초기에 검토한 baseTime 필드는 따로 두지 않고 동일 DTO의 cursor로 통일했다. 요청 cursor에는 현재 DTO에 별도 JsonFormat이 없으므로 ISO 날짜·시간 문자열을 사용한다. spring.mvc.format.date-time은 JSON 본문의 날짜 변환 형식에 적용되지 않는다. 종목이나 봉 주기가 바뀌면 커서를 초기화하고 최초 요청부터 시작한다.

현재 Controller의 @RestController("v1/stock/candle") 값은 URL이 아닌 Bean 이름이다. 별도의 클래스 경로 매핑이 없어 현재 POST 경로는 /이며 기능 테스트도 이를 사용한다. /v1/stock/candle을 사용하려면 @RequestMapping으로 경로를 지정해야 한다.

조회량은 클라이언트 입력으로 받지 않고 서버 내부에서 봉 주기별로 고정한다.

| 봉 주기 | 페이지 크기 초안 |
|---|---:|
| 1분봉 | 390개 |
| 5분봉 | 78개 |
| 15분봉 | 26개 |

정규장 390분의 하루 분량을 기준으로 정한 초안이다. 정규장 외 캔들이 포함되면 실제 기간은 하루와 다를 수 있다. 프론트엔드 구현 후 표시할 캔들 개수와 Prefetch 동작을 확인하여 조정한다. 같은 봉 주기의 최초·연속 요청에는 동일한 크기를 적용한다.

### 2. Response

~~~json
{
  "nextCursor": "2026-10-09T14:58:00",
  "cont-yn": "Y",
  "candles": [
    {
      "time": "20261009145800",
      "open_price": 70000,
      "high_price": 70200,
      "low_price": 69900,
      "close_price": 70100,
      "volume": 12500
    },
    {
      "time": "20261009145900",
      "open_price": 70100,
      "high_price": 70300,
      "low_price": 70000,
      "close_price": 70200,
      "volume": 13000
    }
  ]
}
~~~

목록은 형식을 설명하기 위한 일부 예시다. 현재 응답 DTO의 JSON 이름과 날짜 설정을 반영했다.

| 필드 | 설명 |
|---|---|
| candles | 시간 오름차순 OHLCV 목록 |
| nextCursor | 추가 데이터가 있을 때 반환 목록의 가장 오래된 시각 |
| cont-yn | 더 과거의 데이터가 있으면 Y, 없으면 N |

캔들의 time에는 JsonFormat(pattern = "yyyyMMddHHmmss")이 적용된다. nextCursor에는 별도 날짜 형식 지정이 없어 ISO 문자열로 전달된다. 거래량은 long으로 반환한다.

마지막 페이지는 남은 목록과 cont-yn=N, nextCursor=null을 반환한다. 빈 결과는 candles=[], cont-yn=N, nextCursor=null을 반환한다.

### 3. DB 조회와 페이지 경계

종목·봉 주기를 고정하고 캔들 시각을 기준으로 과거 방향의 Keyset 조회를 수행한다.

- 최초 요청: candle_time <= cursor
- 연속 요청: candle_time < cursor
- DB 정렬: candle_time 내림차순
- DB 조회 개수: 서버 고정 LIMIT + 1
- API 반환 개수: 최대 LIMIT
- 응답 정렬: 반환할 목록을 시간 오름차순으로 변경

LIMIT보다 한 개 더 조회되면 추가 데이터가 있으므로 contYn=Y로 설정한다. 추가 확인용 한 개는 응답에서 제외하고, 실제 반환한 목록의 가장 오래된 시각을 nextCursor로 사용한다. LIMIT 이하이면 contYn=N, nextCursor=null로 설정한다.

연속 요청에서는 커서 시각을 포함하지 않아 이전 페이지의 마지막 캔들이 다음 페이지에 중복되지 않게 한다. 같은 종목·봉 주기 안에서 시각은 유일하므로 시간 커서로 페이지 경계를 정한다. 사용자 요청은 DB에 저장된 범위만 반환한다.

### 4. Prefetch와 클라이언트 병합

1. 종목·봉 주기·기준 시각을 본문에 담고 헤더 cont-yn=N으로 최초 페이지를 요청한다.
2. 반환받은 캔들로 차트를 표시하고 nextCursor·응답의 cont-yn을 보관한다.
3. 과거 방향으로 스크롤할 때 남은 캔들 개수가 실행 기준 이하이면 다음 페이지를 비동기로 요청한다.
4. 헤더 cont-yn=Y와 함께 이전 nextCursor를 본문의 cursor로 전달한다.
5. 반환된 과거 데이터를 기존 목록 앞에 병합하고 차트의 표시 위치를 유지한다.
6. 추가 요청 중에는 같은 다음 페이지를 중복 요청하지 않는다.
7. 응답의 cont-yn=N이면 추가 요청을 중단한다.

Prefetch는 클라이언트에서 실행한다. 서버는 고정 개수의 DB 페이지를 반환하며 사용자의 스크롤 상태를 관리하지 않는다.

## 5. 기능 테스트와 성능 측정

### 1. 기능 테스트

[CandleControllerFunctionalTest.java](../../../../backend/src/test/java/trady/com/backend/candle/controller/CandleControllerFunctionalTest.java)는 MockMvc와 실제 조회 Service·Repository·H2 DB를 연결한다. 직접 만든 캔들로 1·5·15분봉의 페이지 크기, 정렬, 최초 조회의 기준 시각 포함, 연속 조회의 중복 방지와 마지막 페이지를 확인한다. 한글 설명은 DisplayName으로 표시하고 메서드명은 영어로 작성한다.

기능 검증과 성능 측정을 분리하기 위해 이 테스트의 시간 측정·출력 코드는 제거했다. H2 테스트 시간으로 PostgreSQL 조회 성능을 비교하지 않는다.

### 2. PostgreSQL 조회 성능 테스트

[CandleQueryServiceV1PerformanceTest.java](../../../../backend/src/test/java/trady/com/backend/candle/service/CandleQueryServiceV1PerformanceTest.java)는 기존 PostgreSQL 데이터를 사용한다. DataJpaTest에 조회 Service만 Import하고 AutoConfigureTestDatabase(replace = NONE)으로 H2 교체를 막는다. 애플리케이션 전체를 실행하지 않아 토큰 Lifecycle과 동기화 Runner는 실행하지 않는다. 데이터 생성·삭제나 키움 호출도 하지 않는다.

측정 대상은 삼성전자 005930의 1·5·15분봉이다. 워밍업은 각 봉 주기에서 최초 조회 3회이며 통계에서 제외한다.

| 측정 방식 | 조건과 기록 |
|---|---|
| 단일 조회 | 2026-10-09 23:59:59를 기준으로 같은 최초 요청을 10회 반복. 각 호출 시간·반환 개수 기록 |
| 기간 연속 조회 | 2026-10-09 23:59:59부터 2025-10-08 00:00:00까지 과거 방향으로 탐색. 최초·연속 페이지별 시간·반환 개수 기록 |

기간 하한에 도달하거나 DB 데이터가 먼저 소진되면 종료한다. 마지막 페이지가 하한보다 과거의 캔들을 포함할 수 있어 전체 반환 개수와 기간 내 개수를 별도로 집계한다. 데이터 소진으로 끝났다는 결과가 1년치 데이터 보유를 의미하지는 않는다.

측정 구간은 Service 호출이며 트랜잭션·DB 조회·엔티티 로딩·DTO 구성을 포함한다. HTTP·JSON 직렬화는 제외한다. 로그 출력·검증·JSON 파일 저장은 측정 구간 밖에서 수행한다. 평균·중앙값·최댓값과 호출 시간 합계를 출력하며, 연속 조회의 통계에는 최초 페이지도 포함한다.

테스트에는 candle-performance 태그를 사용한다. 기본 실행에서 제외하려면 Gradle test 작업의 excludeTags에 해당 태그를 등록하고 IDE JUnit으로 개별 실행한다.

### 3. 버전별 결과 저장

Repository와 Service는 각각 버전을 관리한다. 현재 비교 대상은 CandleQueryRepositoryV1과 CandleQueryServiceV1이며 파일명에는 RepoV1-ServiceV1을 사용한다. 저장 형식은 [성능 측정 기록 규칙](<../../../../backend/docs/performance/성능 측정 기록 규칙.md>)을 따른다.

~~~text
backend/docs/performance/candle-query/
├─ 1. 단일 조회/
│  └─ RepoV1-ServiceV1-yyyyMMdd-HHmmss.json
└─ 2. 기간 연속 조회/
   └─ RepoV1-ServiceV1-yyyyMMdd-HHmmss.json
~~~

한 실행의 봉 주기별 결과는 각 측정 방식의 JSON 한 파일에 모은다. 같은 버전을 다시 실행해도 실행 시각으로 파일을 구분하며 기존 실행을 덮어쓰지 않는다. 파일명이 겹치면 추가 시각 정보를 붙인다. 해당 실행 안에서는 봉 주기별 결과가 완료될 때 같은 파일에 누적 저장한다.

JSON에는 Repository·Service 버전, 측정 시각, service 측정 범위, 종목·봉 주기·페이지 크기·워밍업 횟수와 전체 통계를 기록한다. 단일 조회는 measurementCount와 호출별 결과를, 기간 조회는 pageCount와 페이지별 커서·시간·반환 개수·기간 내 개수·응답 커서·연속 여부 및 종료 사유를 기록한다. measurementCount는 워밍업을 제외한 반복 호출 수이고 pageCount는 최초 요청을 포함한 측정 페이지 호출 수다.

실제 데이터·조회 조건·워밍업·환경을 동일하게 유지해 개선 전후를 비교한다. 사용자는 최초 1분봉 조회에서 약 1,000ms를 관찰했으며, 반복 측정 통계와 버전별 JSON 결과를 근거로 개선 효과를 비교한다. 이번 결과 저장 구현은 컴파일과 임시 폴더의 JSON 저장·통계 계산을 확인했으며 새로운 PostgreSQL 측정값을 생성하지 않았다.
