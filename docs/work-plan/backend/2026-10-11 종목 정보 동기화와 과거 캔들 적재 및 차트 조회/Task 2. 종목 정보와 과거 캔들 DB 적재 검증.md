### 실행 방법

IDE에서 저장 테스트 클래스 또는 개별 테스트 메서드를 실행한다. 두 클래스는 별도 제외 태그가 없어 Gradle 기본 test 작업에도 포함된다.

직접 만든 입력 데이터를 실제 저장 서비스에 전달한다. Mock을 사용하지 않으며, @DataJpaTest와 @Import로 JPA와 검증할 저장 서비스를 구성한다. H2 메모리 DB에 저장한 뒤 flush()로 SQL을 실행하고 clear()로 영속성 컨텍스트를 비운 다음 다시 조회한다. 각 테스트의 데이터는 종료 시 롤백한다.

2026-10-12 로컬 JUnit Platform 실행에서 종목 저장 3개와 캔들 저장 3개, 총 6개 테스트가 통과했다. 실행 기록에서 INSERT와 기존 엔티티 변경에 따른 UPDATE를 확인했다. 테스트 실행은 로컬 의존성을 사용한 JUnit 실행이며 Gradle 전체 테스트 실행 결과는 아니다.

### 주의 사항

이 검증은 H2에서 저장 동작을 확인한 결과다. PostgreSQL에서의 실행 결과나 실제 키움 API → Runner → DB 전체 수집 결과로 해석하지 않는다. StockSyncService와 StockCandleSyncService의 실제 호출 테스트는 삭제되어 이번 결과 근거에 포함하지 않는다.

테이블·컬럼 이름이 SQL 예약어와 충돌하지 않도록 테스트에 globally_quoted_identifiers=true를 적용했다. 동일 응답 안에서 같은 식별값에 서로 다른 값이 포함되는 경우의 검증은 후속 validation·duplication·outlier 모듈에서 다룬다.

## 4. 검증 결과

### 1. 수집 대상 50종목 선정

| 구분 | 내용 |
|---|---|
| 검증 방법 | 사용자의 시가총액 상위 50종목 조회 결과와 stock-targets.json의 선정 목록 확인 |
| 예상 결과 | 제공할 코스피 주식 50종목의 수집 대상을 명확하게 고정 |
| 실제 결과 | 사용자는 시가총액 기준 목록에 우선주가 섞이는 것을 확인했다. 고정 선정한 목록은 서로 다른 종목 코드 50개이며 종목 코드·이름으로 구성됨 |

자동 시가총액 상위 50개 대신 코스피 인기 종목 50개를 고정 선정했다. stock-targets.json에서 목록을 읽고 DB의 해당 종목을 조회하여 1분·5분·15분봉 수집 대상으로 사용한다. 따라서 이 목록은 매번 순위를 계산한 상위 50종목이 아니다. 종목 정보는 코스피 목록을 보관하고 캔들 수집 대상만 고정 50종목으로 제한한다. DB에 없는 대상 코드는 현재 조회 결과에서 제외되므로, JSON의 50개가 모두 실제 수집되었다는 검증은 이번 기록에 포함하지 않는다.

### 2. 음수 가격의 절댓값 저장

| 구분 | 내용 |
|---|---|
| 검증 방법 | 가격은_절댓값으로_거래량은_그대로_저장한다에서 OHLC가 -100·-120·-90·-110이고 거래량이 50인 응답 데이터를 저장한 뒤 재조회 |
| 예상 결과 | OHLC는 100·120·90·110으로 저장되고 거래량은 50으로 유지 |
| 실제 결과 | 예상한 OHLC 절댓값과 거래량 저장 확인. 테스트 통과 |

키움 응답의 부호가 붙은 가격을 그대로 저장하던 처리를 변경했다. 외부 응답 처리 책임에 맞춰 KiwoomStockCandleResponse.toResponseDto()에서 OHLC에 Math.abs()를 적용하며, Candle 생성자와 updateOhlcv()에는 적용하지 않는다. 거래량은 원래 값으로 전달한다.

### 4. 기존 종목 갱신과 신규 종목 추가

| 구분 | 내용 |
|---|---|
| 검증 방법 | 기존_종목은_갱신하고_신규_종목만_추가한다에서 기존 종목의 이름·시장을 변경하고 신규 종목을 함께 저장 |
| 예상 결과 | 기존 종목의 ID·생성 시각은 유지하고 이름·시장만 갱신. 신규 종목은 추가하고 이번 목록에 없는 기존 종목은 유지 |
| 실제 결과 | 기존 ID·생성 시각 유지와 이름·시장 갱신 확인. 신규 종목 추가 및 응답에 없는 기존 종목 유지로 총 3행 확인. 테스트 통과 |

종목 코드 목록을 IN으로 조회한 뒤 리스트로 비교한다. 교집합은 관리 중인 기존 엔티티를 변경하고 차집합만 saveAll()로 저장한다. 조회·비교·저장은 StockService.savePage()의 같은 트랜잭션에서 수행한다.

### 5. 동일 종목 재저장

| 구분 | 내용 |
|---|---|
| 검증 방법 | 같은_목록을_재저장해도_중복되지_않는다에서 같은 코드·이름·시장의 새 입력 엔티티를 두 번 저장 |
| 예상 결과 | 행이 추가되지 않고 기존 ID 유지 |
| 실제 결과 | 종목 1행과 기존 ID 유지 확인. 테스트 통과 |

### 6. 기존 캔들 충돌 해결과 신규 캔들 추가

| 구분 | 내용 |
|---|---|
| 검증 방법 | 기존_캔들을_갱신하고_새_시각의_캔들만_추가한다에서 같은 종목·15분봉·시각의 OHLCV를 변경하고 새로운 시각의 캔들을 함께 저장 |
| 예상 결과 | 기존 캔들 ID·시각을 유지하면서 OHLCV 갱신. 새로운 시각의 캔들만 추가 |
| 실제 결과 | 기존 ID로 재조회한 캔들의 시각 유지 및 변경된 OHLCV 확인. 총 2행 저장 확인. 테스트 통과 |

ID가 없는 새 Candle 엔티티를 매번 saveAll()로 저장하면 기존의 종목·봉 주기·시각과 유일 제약이 충돌할 수 있었다. 종목·봉 주기를 고정하고 시각 목록을 IN으로 조회하여 기존 행을 먼저 확보하는 방식으로 변경했다. 교집합은 변경 감지로 UPDATE하고, 차집합만 INSERT한다. Map 대신 원본 목록과 조회 목록을 비교하며, StockCandleService.savePage()에서 조회·비교·저장을 같은 트랜잭션으로 처리한다. 기존 ID는 유지하고 이번 응답에 없는 캔들을 삭제하지 않는다.

### 7. 캔들 재저장과 종목·봉 주기 구분

| 구분 | 내용 |
|---|---|
| 검증 방법 | 재저장은_중복되지_않고_종목과_봉주기는_구분한다에서 같은 캔들을 재저장하고, 같은 시각의 첫 종목 1·5·15분봉과 두 번째 종목 1분봉 저장 |
| 예상 결과 | 같은 종목·봉 주기·시각은 중복되지 않고, 종목 또는 봉 주기가 다르면 별도 행으로 저장 |
| 실제 결과 | 총 4행 저장 및 첫 종목 1분봉의 기존 ID 유지 확인. 테스트 통과 |

동일한 종목·봉 주기·시각을 기존 캔들의 식별 기준으로 유지한다. 저장 테스트 6개 통과를 근거로 현재 교집합 갱신·차집합 추가 방식을 유지한다.
