# 분봉 차트 API 스펙 검증

- 작성 날짜: 2026-10-12
- 검증 대상: 키움 모의투자 ka10080의 요청 빈도와 1분·5분·15분봉 응답

## 1. 확인 목적

종목 정보와 과거 캔들을 적재하기 전에 공식 공통 호출 제한을 실제 분봉 요청으로 확인하고, 봉 주기·시간 범위·페이지 크기를 적재 기준으로 정한다.

KiwoomStockClient의 ka10099 종목 목록 조회만으로는 분봉 데이터의 제공 기간과 봉 구간을 확인할 수 없다. 실제 캔들 수집 대상인 ka10080을 호출하는 KiwoomStockCandleClient로 검증 대상을 바꿨다. 종목 정보 적재에서는 KiwoomStockClient를 계속 사용한다.

## 3. 테스트 방법

- 테스트 코드: [backend/src/test/java/trady/com/backend/global/dataloader/kiwoom/stock/client/KiwoomStockCandleClientTest.java](<../../../../backend/src/test/java/trady/com/backend/global/dataloader/kiwoom/stock/client/KiwoomStockCandleClientTest.java>)
- 호출 코드: [KiwoomStockCandleClient.java](<../../../../backend/src/main/java/trady/com/backend/global/dataloader/kiwoom/stock/client/KiwoomStockCandleClient.java>)

### 실행 방법

- IDE에서 테스트를 실행한다.
- @SpringBootTest로 애플리케이션을 준비하고, 기존 Token Lifecycle이 발급한 토큰을 Provider에서 받아 사용한다. DB와 키움 연결 설정이 필요하다.
- 삼성전자 005930, 기준일 20261009, 수정주가 미적용을 공통 조건으로 두고 봉 주기 1·5·15분을 사용한다.
- 단건 응답 시간은 System.nanoTime()으로 Client 호출 전후를 측정한다. 토큰 초기화 시간은 포함하지 않으며 HTTP 응답과 DTO 변환 완료까지 포함한다.
- 요청 빈도는 measureRequests(10, 1000)과 measureRequests(10, 500)으로 비교한다. 초당 2회는 요청 제한 확인용 실험 조건이다.

### 주의 사항

- 같은 토큰으로 다른 요청을 보내지 않는 상태에서 실행한다. 테스트 종료 후 코드가 1초 대기한다.
- 요청은 순차 실행한다. 응답이 지정한 간격보다 오래 걸리면 실제 빈도는 설정한 초당 횟수보다 낮아질 수 있다.
- 초당 2회 테스트는 assertThrows로 429를 예상하며, 429가 발생하는 시점에 종료된다. 실제 성공 횟수와 첫 429 발생 순번은 현재 코드에서 따로 기록하지 않는다.
- 아래 결과는 사용자가 확인한 내용과 현재 남아 있는 실행 로그를 구분한다. 이번 문서 작성 중 실제 API를 다시 호출하지 않았다.

## 4. 검증 결과

### 1. 단건 요청 응답 시간

| 구분 | 내용 |
|---|---|
| 검증 방법 | get1mSingleKiwoomStockCandle, get5mSingleKiwoomStockCandle, get15mSingleKiwoomStockCandle에서 호출 전후의 경과 시간 측정 |
| 예상 결과 | 정상 응답을 받고 단건 HTTP 요청·DTO 변환 소요 시간 확인 |
| 실제 결과 | 현재 Gradle 실행 기록의 5분봉 요청은 2026-10-12 12:35 KST에 179.1388ms 소요. 해당 테스트 성공 확인. 1분·15분봉의 응답 시간 수치는 별도 보관된 기록 없음 |

이 수치는 단건 응답 시간이며 서버의 초당 허용 횟수를 뜻하지 않는다. 요청 빈도는 아래 별도 실험과 공식 안내를 기준으로 정한다.

### 2. 초당 1회 요청

| 구분 | 내용 |
|---|---|
| 검증 방법 | get15mSinglePerSecondKiwoomStockCandle에서 15분봉을 초당 1회 조건으로 10회 요청 |
| 예상 결과 | 공식 모의투자 제한 안에서 10회 요청 완료 |
| 실제 결과 | 사용자 테스트 실행으로 초당 1회 요청이 정상 처리됨을 확인 |

모의투자 적재는 같은 토큰·같은 TR의 요청을 전체 종목과 페이지에 걸쳐 초당 1회로 제어한다.

### 3. 초당 2회 요청

| 구분 | 내용 |
|---|---|
| 검증 방법 | get15mMultiKiwoomStockCandle에서 15분봉을 초당 2회 조건으로 최대 10회 요청하고 TooManyRequests 예외 확인 |
| 예상 결과 | 공식 제한을 초과하는 요청에서 HTTP 429 발생 |
| 실제 결과 | 사용자 테스트 실행으로 429 Too Many Requests 발생 확인 |

초당 2회 요청은 실제 적재 정책으로 사용하지 않는다. 초당 1회 조건의 정상 처리와 비교하여 공식 호출 제한에 부합하는 동작을 확인했다.

### 4. 1분·5분·15분봉 페이지 크기

| 구분 | 내용 |
|---|---|
| 검증 방법 | 세 단건 조회 메서드에서 response.list().size() 확인 |
| 예상 결과 | 각 봉 주기의 한 페이지 응답 건수 확인 |
| 실제 결과 | 사용자 확인 결과 1분·5분·15분봉 모두 한 페이지에 900개 반환. 현재 남아 있는 5분봉 실행 로그에서도 900개 확인 |

900개는 이번에 확인한 페이지 크기다. 마지막 페이지나 데이터가 적은 구간까지 항상 900개라고 가정하지 않으며, 전체 제공 범위는 연속 조회로 수집한다. 현재 Candle Client 테스트는 단건 조회와 요청 빈도를 확인하고, 연속 조회 연결은 DB 적재 단계에서 구현한다.

### 5. 봉 시각과 거래 시간대

| 구분 | 내용 |
|---|---|
| 검증 방법 | 1분·5분·15분봉 응답의 time 값을 사용자 확인 |
| 예상 결과 | 봉 시각의 구간 의미와 반환되는 거래 시간대 확인 |
| 실제 결과 | 사용자 확인 결과 1분봉 09:10은 09:10:00~09:10:59 구간. 15분봉은 09:00~19:45 시각이 관찰됨. 1분·5분봉에서 15:35~16:00 구간, 15분봉에서 15:45 시각의 봉이 관찰되지 않음 |

봉 시각은 구간 시작 시각으로 저장한다. 관찰한 종목·거래일의 응답을 그대로 적재하며, 장후 시간외 종가 거래까지 포함된다고 단정하거나 관찰되지 않은 시간대의 봉을 임의로 생성하지 않는다.

### 6. ka10080 과거 제공 기간

| 구분 | 내용 |
|---|---|
| 검증 방법 | 사용자가 확인한 키움의 분봉차트조회요청 ka10080 제공 기간 안내 참고 |
| 예상 결과 | 최초 과거 캔들 적재에 적용할 조회 기간 기준 확인 |
| 실제 결과 | 키움 안내에 따르면 ka10080은 모의·실전 동일하게 최대 1년 제공. 1년 전체 구간의 수집 실험은 미수행 |

최초 분봉 수집 기간은 최대 1년 제공 안내를 기준으로 정한다. 이 제한은 ka10080에 대한 안내이며, 다른 TR의 제공 기간이나 DB에 보관할 수 있는 기간을 제한하지 않는다.
