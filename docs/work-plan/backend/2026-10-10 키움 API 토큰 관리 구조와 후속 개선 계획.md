# 키움 API 토큰 관리 구조와 후속 개선 계획

## 1. 작업 목표

- 시작 시 토큰 준비, 요청 시 유효성 확인·재발급, 정상 종료 시 폐기의 역할과 관계를 정의한다.
- 운영 중 갱신과 서버 종료용 폐기를 별도 동작으로 설계할 근거를 남긴다.
- 재발급 시 기존 토큰의 처리 정책 확인과 별도 갱신 모듈 추가를 향후 개선 과제로 정의한다.

현재 요청 시점의 재발급은 새 토큰으로 보관 값을 교체하며 기존 토큰을 원격 폐기하지 않는다. 종료용 폐기는 종료 상태로 전환하므로 운영 중 갱신에 그대로 사용할 수 없다. 이 차이를 기준으로 이후 개선 구조를 결정한다.

| 구분 | 내용 |

| 개선 방향 정의 | 운영 중 갱신과 종료용 폐기의 경계, 정책 확인이 필요한 부분 설명 |

갱신 시점, 주기, 재시도 방식과 이전 토큰의 원격 폐기 여부는 후속 정책 확인을 바탕으로 정한다.

## 4. 동작 구조

### 개요

현재 구조의 시작 흐름은 Token Lifecycle → Token Provider → Auth Client → Kiwoom REST API다. Token Provider는 발급 응답을 검증하고 토큰과 만료 시각을 보관한다.

사용 흐름은 Market API Client → Token Provider → 현재 토큰 확인이다. 토큰이 없거나 만료가 가까우면 발급 경로로 진행하고, 새 토큰을 검증한 뒤 교체한다.

정상 종료 흐름은 Token Lifecycle → Token Provider의 종료 상태 전환 → Auth Client → 원격 폐기다. 폐기가 성공하면 보관한 값을 제거한다.

향후 Token Renewal Module은 운영 중 갱신 시점을 관리하고 Token Provider에 갱신을 요청한다. 갱신은 종료 상태로 전환하지 않으며, 종료용 동작은 신규 작업과 갱신을 중단한 뒤 현재 토큰의 폐기를 담당한다. 기존 토큰의 별도 원격 폐기는 키움 정책 확인 후 필요 여부를 결정한다.

### 동작 구조를 선택한 이유

| 책임 분리 | 기대하는 효과 |
|---|---|
| 갱신 시점과 토큰 발급 | 갱신 시점 정책을 바꿔도 인증 통신과 발급 검증을 재사용한다. |
| 운영 중 갱신과 종료용 폐기 | 갱신 때문에 종료 상태로 전환되어 이후 요청이 차단되는 문제를 방지한다. |
| 정책 확인과 기존 토큰 폐기 도입 | 동일 토큰 재발급이나 폐기 영향 때문에 사용할 토큰을 무효화하는 상황을 피한다. |
| 작업 정리와 토큰 폐기 | 진행 중 요청이 사용하는 토큰을 먼저 폐기하는 상황을 방지한다. |

## 6. 단계별 작업 내용

### Task 1. 현재 토큰 관리의 책임과 갱신 경계 정의

- 목적: 운영 중 토큰 갱신과 정상 종료 시 폐기가 어떻게 다른지 분명하게 한다.
- 작업 내용: 요청 시점에 만료를 확인해 재발급하는 흐름, 토큰 요청이 없으면 갱신하지 않는 구조, 종료용 폐기의 종료 상태 전환을 설명한다.
- 작업 내용: 새 토큰 검증 후 교체와 기존 토큰 원격 폐기를 별도 판단으로 구분한다.

### Task 2. 향후 개선 관계와 선행 확인 항목 정의

- 목적: 갱신 모듈과 기존 토큰 폐기 정책을 근거 없이 구현하지 않도록 개선 순서를 남긴다.
- 작업 내용: 키움의 동일 토큰 반환 여부, 이전 토큰 유효성 변화, 폐기의 영향 범위를 확인해야 한다는 조건을 구조도 문서에 반영한다.
- 작업 내용: 갱신 모듈 → Token Provider 관계와 정상 종료 시 신규 갱신 중단 → 진행 작업 정리 → 폐기 관계를 향후 설계로 설명한다.
- 작업 내용: 실제 정책 확인과 갱신 모듈 구현은 이번 문서 작업의 후속 개선 체크리스트에 둔다.
