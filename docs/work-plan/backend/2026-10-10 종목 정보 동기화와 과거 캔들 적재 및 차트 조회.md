# 종목 정보 동기화와 과거 캔들 적재 및 차트 조회

- 작업 날짜: 2026-10-10
- 작업 영역: backend
- 관련 계획: [동기화·차트 조회 구현 계획](../../superpowers/plans/2026-10-10-market-data-sync-and-chart-query.md)

## 1. 작업 목표

- 키움 API의 실제 응답 범위와 호출 비용을 확인한 뒤 제공할 종목 수, 봉 주기, 과거 수집 기간을 결정한다.
- 선정한 종목의 이름·시장 등 기본 정보와 과거 OHLCV 캔들을 별도로 수집하여 DB에 저장한다.
- 수동 실행 시 즉시 한 번 적재하고, 주기 실행 시 같은 동기화 작업을 반복할 수 있도록 한다.
- 클라이언트가 저장된 종목 정보와 캔들을 조회하는 API 한 개를 제공한다.

차트 응답만으로 종목명과 시장 정보를 모두 확보할 수 있다고 가정하지 않는다. 종목 기본 정보를 먼저 동기화하고 해당 종목에 캔들을 연결한다. 모든 종목과 모든 기간을 미리 적재하는 대신, 외부 API의 제약과 실제 처리 비용 안에서 제공 범위를 정한다.

## 4. 동작 구조 

### 개요

한 회차 동기화는 종목 기본 정보 동기화가 끝난 뒤 과거 캔들 적재를 수행한다.

1. 수집 프로세스 잠금을 획득하고 토큰을 준비한다.
2. 종목 API를 조회하여 선정 종목의 기본 정보를 변환·검증하고 저장한다.
3. 선정 종목과 봉 주기별로 차트 API를 순차 조회한다.
4. 외부 응답을 내부 OHLCV 형식으로 변환하고 검증한다.
5. 목표 기간에 해당하는 확정 봉을 페이지 단위로 저장한다.
6. 수집 건수·시간 범위·오류·종료 이유를 기록한다.

조회 흐름은 클라이언트 → ChartController → ChartQueryService → DB → 응답이다. 조회 시 외부 종목·차트 API를 호출하거나 없는 데이터를 자동으로 수집하지 않는다.

### 동작 구조를 선택한 이유

| 책임 | 분리해서 얻는 효과 |
|---|---|
| 외부 API 호출 | 인증·헤더·연속 조회 규격이 바뀌어도 저장과 조회 로직의 변경을 줄일 수 있다. |
| 종목 정보 동기화 | 종목명·시장 변경을 캔들 변환과 분리하고, 기존 종목 ID를 유지하면서 갱신할 수 있다. |
| 캔들 변환 | 문자열 가격·시각의 해석을 별도로 검증하고 외부 응답 형식 변경에 대응할 수 있다. |
| 캔들 검증 | 필수 값·가격 관계·거래량 오류를 저장 전에 차단하고 독립적으로 테스트할 수 있다. |
| 저장 | 동일 데이터를 다시 수집해도 중복 행을 만들지 않아 중간 실패 뒤 재실행할 수 있다. |
| 실행 조율 | 즉시 실행과 스케줄 실행이 같은 동기화 서비스를 사용해 동작 차이를 줄인다. |
| DB 기반 조회 | 수집 중이거나 외부 API가 실패해도 이미 저장된 차트를 조회할 수 있다. |

향후 실시간 수신은 별도 책임으로 추가한다. 이번에는 종목 정보 동기화와 과거 캔들 적재를 구현하며, 스케줄 실행을 실시간 수신으로 간주하지 않는다.

### 실행 모드

| 모드 | 실행 계기 | 수행 작업 | 반복 및 종료 |
|---|---|---|---|
| api | 기본 모드로 애플리케이션 실행 | DB 기반 HTTP 조회 API 제공 | 서버 유지. 토큰 발급·수집·스케줄 등록 없음 |
| sync | 해당 모드를 지정하여 실행 | 웹 서버 없이 즉시 한 회차 동기화 | 토큰 폐기 시도와 잠금 해제 후 종료. 실패는 실패 종료로 전달 |
| scheduler | 해당 모드를 지정하여 실행 | 웹 서버 없이 즉시 한 회차 동기화 | 완료 후 설정된 fixed-delay 간격으로 반복. 정상 종료 시 작업 정리 후 토큰 폐기 |

동일 환경에서 같은 앱키를 사용하는 수집 프로세스는 하나만 실행한다. 기존 계획의 PostgreSQL 세션 잠금을 토큰 발급 전에 획득하고 프로세스가 종료될 때까지 유지한다. 잠금을 얻지 못한 프로세스는 토큰 발급·폐기 없이 종료한다. 서로 다른 DB에서 같은 앱키를 사용하는 실행까지 이 잠금이 보호하지는 않는다.

scheduler 종료는 새 회차 중단 → 진행 중 작업 종료 대기 → 토큰 폐기 → 잠금 해제 순서로 조율한다. 매 회차마다 토큰을 폐기하지 않는다. 강제 종료 시 원격 토큰 폐기를 보장하지 않는다.

첫 구현에서는 확정된 작은 과거 범위를 매회 다시 읽고 중복 키 갱신으로 저장한다. 최신 봉 이후만 읽다가 과거 실패 구간을 놓치는 문제를 피하기 위한 선택이며, 매회 전체 요청 비용을 Task 1에서 확인한다.

## 6. 단계별 작업 내용

### Task 1. API 실측과 제공 범위 결정

- 목적: 실제로 감당할 수 있는 종목 수·봉 주기·과거 기간을 정한 뒤 구현한다.
- 작업 내용: 공식 호출 제한을 확인하고, 한 종목·15분봉·최근 1개월을 초기 실험 조건으로 요청한다. 기존 계획의 최초 자체 예산은 10페이지와 요청 간 최소 2초이며, 공식 제한이 더 엄격하면 그에 맞춘다. 이 값들은 운영 확정값이나 서버 한계가 아니다.
- 작업 내용: 페이지별 건수, 고유 봉 수, 최초·최신 시각, 중복, 소요 시간, 연속 조회 키와 종료 이유를 기록한다. 목표 도달·서버 데이터 종료·자체 예산 소진·오류를 구분한다. 종목명·시장 매핑, 가격 부호, 시각 의미와 시간대, 봉 거래량과 누적 거래량, 진행 중 봉 식별 방법을 확인한다.
- 작업 내용: 후보 조합의 전체 요청 비용을 비교하여 제공 종목, 봉 주기, 개월 수, 거래소·수정주가 정책, 요청 및 스케줄 간격을 사용자와 확정한다.
- 수행 결과 및 근거: 미실행. 공식 자료 링크는 확인했으나 인증된 데이터 요청과 측정 결과는 없다.

### Task 2. 수집 설정과 외부 API 호출 계약 구현

- 목적: 확정된 수집 범위를 설정으로 관리하고 외부 API 통신을 분리한다.
- 작업 내용: 실행 모드·종목·시장·봉 주기·과거 기간·요청 예산을 검증한다. 종목·차트 클라이언트가 한 페이지와 연속 조회 정보를 반환하도록 구현한다. 인증 및 API 구분 헤더, 업무 오류, HTTP 오류, 빈 응답, 연속 조회 키 누락을 처리한다.
- 작업 내용: 자동 테스트는 가짜 응답을 사용하며, 요청 JSON과 헤더가 실제로 전송될 형식을 검증한다.
- 수행 결과 및 근거: 미실행. 기존 클라이언트 골격을 구현 대상으로 확인했다.

### Task 3. 종목 정보 동기화와 캔들 변환·검증 구현

- 목적: 캔들을 연결할 종목 정보를 확보하고 저장 가능한 내부 데이터로 정규화한다.
- 작업 내용: 선정 종목을 연속 조회로 찾아 코드·이름·시장을 저장한다. 기존 종목은 ID와 생성 시각을 유지하면서 이름·시장을 갱신한다. 종목 코드의 앞자리 0을 보존한다.
- 작업 내용: 실측으로 확인한 규칙에 따라 가격과 시각을 변환한다. 누락·형식 오류·범위 초과·음수 거래량·OHLC 관계 오류를 검증한다. 일부 페이지만 확인한 상태를 종목 미지원으로 단정하지 않는다.
- 수행 결과 및 근거: 미실행. 변환 규칙은 Task 1의 응답 의미 확인 후 확정한다.

### Task 4. 과거 캔들 적재와 재실행 구현

- 목적: 확정 기간의 캔들을 저장하고 반복 실행 한다.
- 작업 내용: 회차 기준 시각을 한 번 정하고 종목 정보 동기화 후 종목·주기별로 순차 수집한다. 확정 기간의 완료된 봉만 변환·검증해 페이지 단위의 짧은 트랜잭션으로 저장한다. 외부 API 호출 중 DB 트랜잭션을 유지하지 않는다.
- 작업 내용: 종목·봉 주기·시각의 유일 키를 기준으로 신규 행은 추가하고 기존 OHLCV는 갱신한다. 같은 페이지의 값이 충돌하는 중복, 반복 연속 조회 키, 응답 종목 불일치와 예산 초과를 처리한다. 중간 실패를 전체 성공으로 기록하지 않는다.
- 작업 내용: 매 동기화 실행 시 설정된 과거 기간을 다시 조회한다. 기존 캔들은 갱신하고 누락된 캔들은 추가한다. 수집 구간의 시작과 끝 데이터가 존재하더라도 중간 데이터가 누락될 수 있으므로, 이것만으로 수집 완료를 판단하지 않는다.
- 수행 결과 및 근거: 미실행. PostgreSQL의 실제 유일 제약과 갱신 결과를 테스트 DB에서 검증할 예정이다.

### Task 5. 즉시 실행·주기 실행·종료 연결

- 목적: 동일한 동기화 작업을 일회 실행과 반복 실행에서 재사용한다.
- 작업 내용: api 모드에서는 외부 토큰 발급과 수집을 실행하지 않는다. sync는 즉시 한 회차 실행 후 종료하고, scheduler는 즉시 한 회차 완료 후 fixed-delay로 반복한다.
- 작업 내용: 토큰 발급 전에 전용 DB 연결로 세션 잠금을 획득한다. 종료 시 스케줄 중단, 진행 작업 대기, 토큰 폐기, 잠금 해제 순서를 보장한다. 종료 대기 한도를 넘긴 경우 실패를 기록한다. 폐기 실패를 성공으로 출력하지 않는다.
- 수행 결과 및 근거: 미실행. 현재 Lifecycle과 목표 실행 모드의 차이를 확인했으며 구현 변경은 하지 않았다.

### Task 6. 차트 조회 API 한 개 구현

- 목적: 외부 API를 호출하지 않고 저장된 종목 정보와 캔들을 제공한다.
- 작업 내용: 기존 계획의 제안인 `GET /v1/stock/candle`을 기준으로 종목 코드·봉 주기·시작/종료 시각·조회 개수·이어 읽을 시각을 받는다. 응답에 종목 코드·이름·시장, 봉 주기·시간대, OHLCV 목록과 다음 페이지 정보를 포함한다.
- 작업 내용: 시작 포함·종료 제외 구간을 시간 오름차순으로 읽고, 마지막 봉 시각 이후로 이어 읽는다. 미제공·미등록 종목은 404, 잘못된 조건은 400, 등록 종목의 빈 구간은 200과 빈 목록으로 처리하는 계약을 검토한다.
- 작업 내용: 조회 개수 기본 1,000·상한 5,000은 기존 계획의 서비스 보호 정책 제안이며 키움 요청 제한이 아니다. 상세 요청·응답과 오류 계약은 구현 전 사용자 검토 후 확정한다.
- 수행 결과 및 근거: 미실행. API 경로와 상세 계약은 기존 구현 계획의 제안 단계다.

### Task 7. 전체 흐름 검증과 최종 기록

- 목적: 처음 정의한 작업 구조대로 수집·저장·조회가 연결되는지 확인하고 결과와 설계 근거를 남긴다.
- 작업 내용: 가짜 외부 응답과 별도 PostgreSQL 테스트 DB로 전체 흐름을 검증한다. 동일 자료 재적재, 중간 실패 후 복구, 잠금 충돌, 스케줄 실패 후 다음 회차, 종료 순서, 외부 호출 없는 조회를 확인한다.
- 작업 내용: 실측으로 확정한 소규모 범위에서 실제 sync·scheduler·api 동작을 확인하고 관련 테스트와 리뷰를 수행한다. 실제 호출 및 DB 적재는 구현 작업에서 실행하며 이번 문서 작성에는 포함하지 않는다.
- 작업 내용: 정의한 목적·구조·단계와 실제 결과를 비교한다. 달라진 내용과 이유를 사용자에게 알리고 검토 후 본 문서의 검증 결과와 최종 기록에 반영한다.
- 수행 결과 및 근거: 미실행. 완료 후 실제 검증 근거와 비교 결과를 기록한다.
