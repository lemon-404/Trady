
# Trady 데이터베이스 테이블 역할 및 책임

Trady 데이터베이스는 차트 조회, 주문·체결, D+2 결제, 계좌 현황의 네 가지 핵심 기능을 지원하기 위해 총 9개의 주요 테이블로 구성한다. 각 테이블은 데이터의 책임을 분리하여 주문 원본, 현재 호가 상태, 체결 이력, 결제 상태 등이 서로 독립적으로 관리될 수 있도록 구성한다.

| 테이블 | 역할 | 핵심 책임 |
|---|---|---|
| `member` | 사용자 관리 | 사용자 식별 및 기본 정보 관리 |
| `stock` | 종목 마스터 | 거래 및 차트 조회 대상 종목 관리 |
| `stock_candle` | 차트 데이터 | 종목별·봉 단위 OHLCV 시계열 데이터 관리 |
| `account` | 계좌 관리 | 계좌의 현금 및 주문가능금액 관리 |
| `position` | 보유종목 관리 | 계좌별 종목 보유수량 및 평균매입가 관리 |
| `order` | 주문 관리 | 사용자가 제출한 주문 원본 및 주문 상태 관리 |
| `order_book` | 호가창 관리 | 현재 체결 가능한 미체결 주문과 잔량 관리 |
| `execution` | 체결 관리 | 주문 간 실제 체결 결과 및 체결 이력 관리 |
| `settlement` | 결제 관리 | 체결에 따른 D+2 결제 예정 및 처리 상태 관리 |

---

## 1. `member`

**역할:** Trady를 사용하는 사용자의 기본 정보를 관리한다.

**책임:** 사용자 식별에 필요한 이메일, 비밀번호, 이름 등의 기본 정보를 저장하며 사용자와 계좌를 연결하는 기준 엔티티 역할을 한다.

**목적:** Trady 프로젝트에서 회원 기능 자체는 핵심 구현 대상이 아니므로 복잡한 사용자 관리 기능보다는 계좌 및 거래 데이터를 사용자 단위로 구분할 수 있는 최소한의 식별 정보를 제공한다. 프로젝트에서도 사용자 기능은 성능 및 동시성 테스트를 위한 최소한의 식별 기능을 중심으로 구현한다. 프론트엔드 프로젝트 기능 및 구현 범위 v1

**기본키(PK):** `member_id`

---

## 2. `stock`

**역할:** 거래 및 차트 조회 대상이 되는 주식 종목의 기준 정보를 관리한다.

**책임:** 종목 코드, 종목명, 시장 구분 등 종목 자체의 정보를 관리하고 `stock_candle`, `position`, `order`, `order_book`, `execution` 등에서 동일한 종목을 참조할 수 있도록 종목 마스터 역할을 한다.

**목적:** 여러 기능에서 반복적으로 사용되는 종목 정보를 하나의 기준 데이터로 관리하여 종목 식별 기준을 일관되게 유지한다.

---

## 3. `stock_candle`

**역할:** 주식 차트 조회에 사용되는 OHLCV 시계열 데이터를 관리한다.

**책임:** 종목과 봉 주기(`interval`), 기준 시각(`candle_time`)을 기준으로 시가, 고가, 저가, 종가, 거래량을 저장한다. 동일한 종목이라도 시간과 봉 주기에 따라 여러 개의 데이터가 존재한다.

**목적:** 대규모 시계열 데이터를 구축하여 차트 조회 기능을 제공하고, 데이터 규모 증가에 따른 조회 성능 저하와 인덱스·파티셔닝·캐시 등의 최적화 효과를 실험하는 핵심 데이터로 사용한다. 프로젝트에서는 OHLCV 데이터를 기반으로 기간별 차트 조회와 데이터 규모 증가에 따른 성능 측정을 수행하는 것을 목표로 한다. 프로젝트 배경 및 추진 목적 v1

식별 기준은 논리적으로 다음과 같다.

```text
stock_id + interval + candle_time
```

---

## 4. `account`

**역할:** 사용자 계좌의 전체적인 금전 상태를 관리한다.

**책임:** 사용자가 보유한 현금과 현재 새로운 주문에 사용할 수 있는 주문가능금액을 관리한다. 주문 접수, 체결, 결제 과정에서 발생하는 계좌 금액 변화를 반영한다.

**목적:** 여러 주문이 동시에 동일 계좌에 접근하는 상황에서도 실제 보유 금액을 초과하는 주문이 발생하지 않도록 계좌의 금전 상태에 대한 기준 데이터를 제공한다. 특히 동시 주문에서 주문가능금액의 정합성을 검증하는 핵심 테이블이다. 프로젝트 배경 및 추진 목적 v1

`account`는 **계좌 전체의 금전 상태**를 담당하고, 종목별 보유 상태는 `position`에 위임한다.

---

## 5. `position`

**역할:** 계좌별 보유종목 상태를 관리한다.

**책임:** 특정 계좌가 특정 종목을 몇 주 보유하고 있는지와 평균매입가를 관리한다. 매수·매도 체결 결과에 따라 보유수량과 평균매입가가 변경된다.

**목적:** 계좌 전체 금액을 관리하는 `account`와 종목별 보유 상태를 분리하고, 매도 주문 시 보유수량 검증 및 계좌 현황 조회에 필요한 데이터를 제공한다. 프로젝트에서는 보유종목, 보유수량, 평균매입가 등을 계좌 현황의 주요 정보로 관리한다. 백엔드 프로젝트 기능 및 구현 범위 v1

하나의 계좌에는 동일 종목 Position이 하나만 존재하도록 논리적으로 다음 제약을 가진다.

```sql
UNIQUE(account_id, stock_id)
```

---

## 6. `order`

**역할:** 사용자가 제출한 **주문의 원본 정보와 주문 상태**를 관리한다.

**책임:** 주문 계좌, 종목, 매수·매도 구분, 시장가·지정가 구분, 주문가격, 최초 주문수량 및 현재 주문 상태를 관리한다. 주문이 부분 체결되거나 전량 체결되더라도 주문 자체는 삭제하지 않고 기록으로 유지한다.

**목적:** 사용자가 어떤 주문을 제출했으며 그 주문이 현재 어떤 상태인지 추적하기 위한 기준 데이터를 제공한다. `order_book`과 분리함으로써 영속적으로 보존해야 하는 주문 정보와 현재 매칭에 필요한 데이터를 분리한다.

프로젝트에서 지정가·시장가 주문과 접수, 미체결, 부분 체결, 체결 완료 등의 주문 상태를 관리하도록 정의하고 있다. 백엔드 프로젝트 기능 및 구현 범위 v1 백엔드 프로젝트 기능 및 구현 범위 v1

즉,

```text
order = 사용자가 무엇을 주문했는가?
```

를 담당한다.

---

## 7. `order_book`

**역할:** Matching Engine이 사용하는 **현재 활성 상태의 미체결 주문**을 관리한다.

**책임:** 현재 매칭 가능한 종목, 매수·매도 방향, 주문가격, 미체결 잔량, 시간 우선순위를 관리한다. 부분 체결이 발생하면 잔량을 감소시키고 전량 체결되거나 취소된 주문은 Order Book에서 제거한다.

**목적:** 전체 주문 이력을 관리하는 `order`와 현재 매칭 대상만 관리하는 `order_book`을 분리하여 Matching Engine이 필요한 데이터에 집중할 수 있도록 한다. 또한 가격·시간 우선 원칙에 따른 상대 주문 탐색 및 향후 Order Book 조회 성능 최적화의 대상으로 활용한다.

프로젝트에서도 호가창에서 미체결 매수·매도 주문의 가격, 수량, 미체결수량, 접수 순서를 관리하고 가격·시간 우선 원칙에 따라 체결하도록 정의하고 있다. 백엔드 프로젝트 기능 및 구현 범위 v1

즉,

```text
order      = 주문 원본/상태
order_book = 지금 매칭할 수 있는 주문의 현재 상태
```

로 책임을 구분한다.

---

## 8. `execution`

**역할:** Matching Engine에 의해 실제로 발생한 **체결 결과를 이력으로 기록**한다.

**책임:** 서로 매칭된 매수 주문과 매도 주문, 체결 종목, 체결 가격, 체결 수량, 체결 시각을 저장한다. 하나의 주문이 여러 상대 주문과 부분 체결될 경우 체결이 발생할 때마다 새로운 `execution`을 생성한다.

**목적:** 주문 상태와 실제 거래가 성립한 사실을 분리하고, 부분 체결을 포함한 모든 체결 결과를 추적할 수 있도록 한다. 또한 계좌 보유수량 변경과 D+2 결제 데이터 생성의 기준 데이터 역할을 한다.

예를 들어 하나의 100주 주문이 `30 + 50 + 20`주로 나누어 체결되면:

```text
Order #1 : 100주

Execution #1 : 30주
Execution #2 : 50주
Execution #3 : 20주
```

처럼 세 건의 체결 이력이 생성된다.

따라서 `execution`은 현재 상태를 계속 수정하는 테이블이라기보다 **발생한 체결 사실을 누적 기록하는 테이블**이라는 점이 중요하다.

---

## 9. `settlement`

**역할:** 체결에 따라 발생하는 **D+2 결제 예정 데이터와 결제 처리 상태**를 관리한다.

**책임:** 어떤 체결에서 발생한 결제인지, 어떤 계좌의 매수·매도 결제인지, 결제 금액, 거래일, 결제 예정일, 처리 상태 및 실제 처리 시각을 관리한다.

부분 체결도 독립적인 거래이므로 `execution`이 생성될 때마다 해당 체결을 기준으로 결제 데이터를 생성한다.

```text
Execution
    │
    ├─ 매수 계좌 Settlement
    │
    └─ 매도 계좌 Settlement
```

**목적:** D+2 시점에 처리해야 할 결제 대상을 명확하게 관리하고, 배치 처리 중 실패·중단·재실행이 발생하더라도 이미 처리된 결제가 중복 반영되지 않도록 결제 단위의 처리 상태를 관리한다. 프로젝트에서도 대량 결제 처리, 실패 재처리, 중복 결제 방지 및 멱등성을 핵심 검증 대상으로 정의하고 있다. 백엔드 프로젝트 기능 및 구현 범위 v1

여기서 시간 관련 데이터의 책임은 다음처럼 구분한다.

**`execution.executed_at`**

→ 실제 체결이 발생한 정확한 시각

**`settlement.trade_date`**

→ 해당 거래의 거래일

**`settlement.settlement_date`**

→ D+2 결제 예정일

**`settlement.processed_at`**

→ 실제 결제 처리가 수행된 시각
