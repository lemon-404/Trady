
# Trady 프로젝트 배경 및 추진 목적 v1

## 1. 프로젝트 추진 배경

기존 Trady는 차트 분석, 보조지표, 모의 투자, 자동매매, AI 분석 등 다양한 기능을 제공하는 트레이딩 플랫폼을 목표로 기획하였다.

그러나 취업용 개인 프로젝트의 목적을 다시 검토하면서 다양한 사용자 기능을 구현하는 것보다, 실제 백엔드 시스템에서 발생할 수 있는 **대규모 데이터 처리, 조회 성능, 동시성, 데이터 정합성, 장애 및 재처리** 등의 문제를 직접 경험하고 해결하는 것이 중요하다고 판단하였다.

이에 따라 기존 Trady의 기능을 대폭 축소하고, 백엔드 기술적 문제를 집중적으로 경험할 수 있는 **모의 주식 거래 시스템**으로 프로젝트 방향을 재설정한다.

프로젝트의 핵심 기능은 다음 네 가지로 구현한다.

- 주식 차트 조회
- 주식 주문·체결
- D+2 결제
- 계좌 현황

각 기능을 단순히 구현하는 것에 그치지 않고, **작은 규모에서 정상적으로 동작하는 시스템부터 시작하여 데이터와 동시 사용자 규모를 단계적으로 확장하면서 각 규모를 안정적으로 처리할 수 있는 시스템으로 발전시키는 것**을 프로젝트의 핵심 방향으로 한다.

## 2. 모의 주식 거래 시스템을 선정한 이유

### 2.1 대규모 시계열 데이터를 활용한 조회 성능 최적화

개인 프로젝트에서는 실제 서비스 수준의 대규모 데이터를 확보하기 어렵다.

예를 들어 게시글이나 사용자 활동 데이터와 같이 사용자의 입력을 통해 생성되는 데이터는 실제 사용자가 많지 않은 개인 프로젝트 환경에서는 충분한 규모로 축적되기 어렵다.

반면 주식 차트 데이터는 종목별 가격 변화가 시간에 따라 지속적으로 기록되는 시계열 데이터이므로 서비스 특성 자체에서 대량 데이터가 발생한다.

본 프로젝트에서는 국내 주식시장 정규 거래시간인 **09:00~15:30**을 기준으로 15분봉 OHLCV 데이터를 관리한다.

정규장은 하루 390분이므로 하나의 종목에서 거래일당 최대 약 26개의 15분봉 데이터가 생성된다.

이를 1,000개 종목으로 확대하면 다음과 같다.

**1종목**

390건 / 거래일

**1,000종목**

390,000건 / 거래일

**연간 250거래일 가정**

약 97,500,000건

따라서 약 1년의 데이터만으로도 1억 건에 가까운 시계열 데이터를 구성할 수 있다.

이를 이용하여 데이터 규모가 증가하면서 발생하는 조회 성능 저하를 직접 확인하고, 특정 종목의 특정 기간에 해당하는 차트 데이터를 빠르게 조회할 수 있도록 데이터베이스 구조를 개선한다.

이를 통해 인덱스, 쿼리 실행 계획, 파티셔닝, 캐시 등 대규모 데이터 조회에 필요한 기술을 실제 데이터와 측정 결과를 기반으로 학습하는 것으로 데이터베이스 성능 최적화 경험을 목표로 한다.

### 2.2 주문·체결

#### 2.2.1 빠른 처리와 높은 정합성이 동시에 요구되는 주문·체결

주식 주문은 짧은 시간 동안 여러 요청이 집중될 수 있으며 하나의 계좌에 여러 주문이 동시에 접근할 수 있다.

따라서 주문을 빠르게 처리하는 것뿐만 아니라 **계좌의 주문가능금액과 보유수량이 항상 정확한 상태를 유지하는 것**이 중요하다.

예를 들어 주문가능금액이 100만 원인 계좌에서 70만 원의 매수 주문 두 개가 동시에 발생했다고 가정한다.

두 요청이 동시에 기존 주문가능금액 100만 원을 조회하여 각각 주문이 가능하다고 판단한다면 총 140만 원의 주문이 처리되는 문제가 발생할 수 있다.

```text
주문 A ─┐
        ├─→ 주문가능금액 1,000,000원 조회
주문 B ─┘

주문 A → 700,000원 매수 가능
주문 B → 700,000원 매수 가능

결과
→ 실제 보유 금액을 초과한 주문 발생 가능
```

본 프로젝트에서는 다수의 주문 요청이 동시에 발생하는 환경을 구성하고, 여러 요청이 동일한 계좌 상태에 접근하더라도 잔액 및 보유 수량의 데이터 정합성이 유지되도록 주문 처리 구조를 구현한다.

이 과정에서 트랜잭션, 동시성 제어, Lock, 멱등성 등을 활용하여 Race Condition과 중복 주문 등의 문제를 해결한다.

또한 강한 동시성 제어를 적용할수록 데이터 정합성은 확보하기 쉬워지는 반면 Lock 경합 등에 의해 처리량과 응답속도가 저하될 수 있다.

따라서 단순히 주문이 정상적으로 처리되는 것에서 끝내지 않고 **정합성과 처리 성능 사이의 Trade-off를 직접 측정하고 적절한 처리 구조를 찾는 것**을 목표로 한다.

---

#### 2.2.2 주문 처리 과정에서의 동시성 및 처리 순서 경험

주식 주문에서는 짧은 시간 동안 여러 주문이 동시에 발생할 수 있다.

특히 동일한 계좌에 여러 주문이 동시에 접근하면 주문 처리 순서에 따라 주문가능금액과 보유수량의 최종 상태가 달라질 수 있다.

따라서 다음과 같은 문제를 고려해야 한다.

- 여러 주문이 동시에 들어왔을 때의 처리 방법
- 동일 계좌에 대한 동시 접근 제어
- 주문 처리 도중 실패했을 경우의 상태 복구
- 동일한 주문 요청이 반복되었을 경우의 중복 처리 방지
- 재시도 상황에서도 동일한 결과를 보장하는 방법
- 데이터 정합성을 유지하면서 처리 성능을 확보하는 방법

이러한 문제를 해결하면서 단순 CRUD API 구현을 넘어 **여러 요청이 동시에 하나의 상태를 변경하는 환경에서 안정적인 비즈니스 로직을 설계하는 경험**을 확보한다.

---

#### 2.2.3 주문 매칭 엔진

실제 거래소에서는 접수된 매수 주문과 매도 주문의 가격 및 수량을 비교하고, 정해진 거래 규칙에 따라 주문을 체결하는 **주문 매칭 엔진(Matching Engine)**이 사용된다.

Trady에서는 실제 거래소 수준의 고도화된 주문 시스템을 구현하는 것을 목표로 하지 않고, 주문이 접수되고 호가창에 등록된 후 조건에 맞는 상대 주문과 체결되는 기본적인 과정을 직접 구현해본다.

이를 위해 다음과 같은 주문 처리 개념과 거래 규칙을 적용한다.

- **호가창(Order Book)**
  - 아직 체결되지 않은 매수·매도 주문을 가격별로 관리한다.

- **매수호가 / 매도호가(Bid / Ask)**
  - 매수 주문과 매도 주문의 가격 및 수량을 관리하고 체결 가능한 상대 주문을 탐색하는 기준으로 사용한다.

- **지정가 주문(Limit Order)**
  - 사용자가 원하는 매수 또는 매도 가격을 지정하여 주문하고, 해당 가격 조건을 만족하는 상대 주문이 존재할 경우 체결한다.

- **시장가 주문(Market Order)**
  - 가격을 직접 지정하지 않고 현재 호가창에서 체결 가능한 상대 주문을 기준으로 거래한다.

- **가격·시간 우선 원칙(Price-Time Priority)**
  - 더 유리한 가격의 주문을 우선하여 처리하고, 동일한 가격에서는 먼저 접수된 주문을 우선하여 체결한다.

- **부분 체결(Partial Fill)**
  - 주문 수량 전체를 한 번에 체결할 수 없는 경우 체결 가능한 수량만 먼저 처리하고 나머지 수량은 미체결 상태로 관리한다.

- **주문 매칭(Matching)**
  - 호가창에 존재하는 매수·매도 주문의 가격과 수량을 비교하여 체결 가능 여부를 판단하고, 체결 가격과 체결 수량을 결정한다.

**호가창 관리, 가격·시간 우선 원칙, 부분 체결과 같은 핵심 주문 처리 과정을 직접 구현하여 주문이 어떤 규칙과 자료구조를 기반으로 체결되는지 이해하는 것**을 목표로 한다.

또한 다수의 주문이 동시에 유입되는 환경에서 매칭 과정과 계좌 상태 변경이 함께 발생하므로, 이를 기존 프로젝트의 핵심 주제인 **동시성 제어, 데이터 정합성 및 주문 처리 성능**과 연결하여 검증한다.

따라서 Trady의 주문 시스템은 실제 거래소 수준의 완전한 매칭 시스템이 아닌, **핵심 체결 원리를 구현한 단순화된 주문 매칭 엔진**을 구축하는 것을 범위로 한다.

가장 마지막 단계로 나머지 3가지 기능들을 구현해본 후 마지막에 성능 개선을 해보는 것으로 한다.

---

### 2.3 시간에 따라 상태가 변화하는 D+2 결제 처리

주식 거래는 주문이 체결되었다고 해서 모든 업무 처리가 종료되는 것이 아니다.

체결된 거래에 따라 결제 예정 금액이 발생하고 일정 시점 이후 실제 결제 처리가 이루어지는 후속 과정이 존재한다.

본 프로젝트에서는 이를 단순화한 D+2 결제 구조를 구현하여 **즉시 처리되는 API 요청과 다른 시간 기반의 상태 변경 문제**를 경험한다.

D+2 결제에서는 정해진 시점에 여러 결제 데이터를 처리해야 하며, 처리 도중 서버 또는 작업이 실패할 가능성도 고려해야 한다.

예를 들어 10,000건의 결제 데이터를 처리하는 도중 5,000번째에서 작업이 중단되고 다시 실행된다면 이미 처리된 결제가 다시 반영되어서는 안 된다.

따라서 본 프로젝트에서는 다음과 같은 문제를 다룬다.

- 대량 결제 데이터의 배치 처리
- 처리 중 실패한 작업의 재처리
- 동일 결제의 중복 처리 방지
- 재실행 시에도 동일한 결과를 보장하는 멱등성
- 일부 작업 실패 시 데이터 정합성 유지
- 결제 처리 상태 관리

이를 통해 Batch, Transaction, Retry, Idempotency 및 장애 복구와 관련된 백엔드 처리 경험을 확보한다.

---

### 2.4 주문과 결제 결과를 연결하는 계좌 현황

계좌 현황은 주문·체결과 D+2 결제 결과가 최종적으로 사용자 계좌에 정상적으로 반영되었는지 확인하기 위한 기본 기능으로 구현한다.

계좌에서는 다음 정보를 관리한다.

- 현금
- 주문가능금액
- 보유종목
- 평균매입가
- 평가금액
- 평가손익
- 총자산

주문이 발생하면 주문가능금액과 보유수량이 변경되고, 체결 및 D+2 결제 과정에 따라 계좌의 여러 금액 상태가 변화한다.

따라서 계좌 현황은 각각 독립적으로 구현된 주문과 결제 기능을 하나의 일관된 사용자 자산 상태로 연결하는 역할을 한다.

이를 통해 주문 → 체결 → 결제 → 계좌로 이어지는 전체 데이터 흐름의 정합성을 확인한다.

## 3. 프로젝트 추진 목적

모의 주식 거래라는 도메인을 활용하여 일반적인 CRUD 중심 개인 프로젝트에서는 경험하기 어려운 **대규모 데이터 처리, 조회 성능 최적화, 동시성 제어, 데이터 정합성, 배치 처리 및 장애 복구** 문제를 직접 경험하는 것을 목표로 한다.

이를 위해 다음 네 가지 핵심 기능만 구현한다.

### 차트 조회

대규모 OHLCV 시계열 데이터를 구축하고 데이터 증가에 따른 조회 성능 변화를 측정하여 데이터베이스 조회 구조를 최적화한다.

### 주식 주문·체결

동시에 발생하는 주문 요청에서도 Race Condition을 방지하고 데이터 정합성을 유지할 수 있도록 주문 처리 구조를 구현하며, 사용자와 주문 요청 규모를 단계적으로 확대하면서 안정성과 처리 성능을 함께 검증한다.

### D+2 결제

시간에 따라 처리되어야 하는 결제 데이터를 관리하고 배치 실행 중 장애와 재처리 상황에서도 중복 반영되지 않는 안정적인 결제 구조를 구현한다.

### 계좌 현황

주문·체결·결제 결과를 계좌 상태에 일관되게 반영하고 전체 거래 과정의 데이터 정합성을 확인한다.

## 4. 프로젝트 개발 방향

본 프로젝트에서는 처음부터 대규모 트래픽을 처리하기 위한 복잡한 구조를 적용하기보다, **작은 규모에서 정확하게 동작하는 기본 시스템을 먼저 구현하고 데이터와 동시 사용자 규모를 단계적으로 확대하면서 시스템을 발전시키는 방식**으로 개발한다.

먼저 차트 조회, 주문·체결, D+2 결제, 계좌 현황의 핵심 기능을 단순한 구조로 구현하고 각 기능과 전체 거래 흐름이 정상적으로 동작하는지 검증한다.

이후 차트 데이터의 양과 동시 사용자 및 주문 요청 규모를 단계적으로 증가시키면서 현재 시스템이 안정적으로 처리할 수 있는 범위를 측정한다.

전체 개발 과정은 다음을 기본으로 한다.

```text
기본 기능 구현
(차트 조회 / 주문·체결 / D+2 결제 / 계좌 현황)
↓
기능 및 데이터 정합성 검증
(단위 테스트 / 통합 테스트 / API 테스트)
↓
소규모 데이터 및 사용자 환경에서 정상 동작 확인
↓
데이터 및 동시 사용자 규모 단계적 확대
↓
처리량(TPS/RPS), 응답시간(P95/P99), 오류율, 데이터 정합성 측정
↓
현재 시스템의 처리 한계 및 병목 지점 확인
↓
원인 분석 및 개선 방법 검토
↓
현재 규모에서 필요한 기술 및 구조 적용
↓
동일한 조건에서 성능 및 정합성 재측정
↓
개선 전후 결과 비교 및 측정 결과 저장
↓
더 큰 데이터 및 사용자 규모로 확장
↓
동일한 과정 반복
```

이 과정에서 특정 기술을 사용하기 위한 목적으로 시스템을 설계하는 것은 지양한다.

**현재 시스템이 어느 정도의 데이터와 요청을 처리할 수 있는지를 먼저 측정하고, 규모가 증가하면서 기존 구조로 처리하기 어려워지는 시점에 필요한 기술을 선택하여 적용한다.**

각 단계에서는 테스트 조건과 처리량, 응답시간, 오류율, 데이터 정합성 등의 결과를 기록하여 시스템이 **어떤 구조에서 어느 정도의 규모까지 처리할 수 있었으며, 구조를 변경한 이후 처리 가능한 범위가 어떻게 변화했는지** 비교할 수 있도록 한다.

이를 통해 최종적으로 단순히 여러 백엔드 기술을 사용한 프로젝트가 아니라, **작은 규모의 시스템에서 시작하여 데이터와 사용자 규모가 증가함에 따라 시스템 구조를 단계적으로 발전시키고 그 과정을 수치로 검증할 수 있는 프로젝트**를 만드는 것을 목표로 한다.
