### 3-1. 앱 전용 온라인 호가창 기반 체결 시스템

로직: 앱 전용 사용자 기반 호가창 구성

소규모 사용자 환경 운영시 실제 활발한 거래과 괴리감이 있다.

### 3-2. 실시간 호가창 기반 체결 시스템 

로직: 실시간 호가창의 매수/매도 잔량을 기준으로 Trady 호가창의 잔량을 체결 시키는 방식

- 실제 투자자들은 실제 거래 환경에서 주문 체결 대기 시간을 가지지만 무의 투자 시스템 사용자들은 이 대기시간을 무시하고 즉시 체결할 수 있다. 

또한 호가창의 동일 잔량이 있을시 체결할 순 있지만 이는 호가창에 동일 잔량이 존재할시 **무한 체결 승인** 버그의 발판이 된다. 

### 3-3. 가상 체결 시스템

위 시스템들의 예상되는 문제들은 소규모 사용자수, 무한 체결 버그가 있었다. 

위 문제를 해결하기 위해서는
실제 주문을 체결 시켰다는 체결 결과 와 한국 거래소(KRX)의 처리 방식과 동일하게 내부 체결 시스템의 주문 요청에 대해 가격우선 시간 우선 원칙에 따라 요청을 정렬해 놓는것이다.

기존 체결 시스템은 다음과 같다. 

주문 요청 > 증권 거래 시스템 전달 > 호가창 잔량 비교 > 대기(가격 우선 원칙 > 시간 우선 원칙) > 체결 의 과정을 거친다. 

기존 체결 시스템의 주문 매칭을 위한 체결 시점에 정렬된 요청 시계열 데이터를 활용할 것이므로 이를 똑같이 구현하되 매칭 방법만 달리 구현한다. 

주문 요청 > 가상 체결 거래 시스템 전달 > 실제 체결 발생 > 대기(가격 우선 원칙 > 시간 우선 원칙) > 실제 매도 채결 ≤ 모의 투자 매수 주문 일때 매칭 > 체결 

의 과정으로 규현한다. 

이 구조가 안될 경우는 체결량이 0인 종목 존재시 불가능 하다. 
하지만 인기 종목 100종목에 한해 서비스 제공중이기 때문에,
체결량이 0인 종목에 대해서 고려하지 않아도 된다.

그리고 하나의 체결에 대해서 n개의 요청을 처리하지않고 

또한 VI 문제도 해결된다. 


>VI (변동성 완화 장치)
>주가가 일정 기간 동안 급격히 상승하거나 하락할 때 시장의 과열을 막고 투자자들에게 냉정하게 생각할 시간을 주기 위해 일정 시간 동안 거래를 일시 중단하는 제도


정리하자면 

**사용자 주문 요청(REST API)**

주문 접수 > 유효성 체크 및 계좌 검증 (Pre-Trade Risk Check)> 필터링 (Compliance Check) > 요청 우선순위 큐 저장 > 가상 체결 시스템에 요청 전달


**가상 체결 시스템(WebSocket)**

요청 접수 > 실시간 체결 이벤트 > 체결 이벤트와 모의 투자 호가창 매칭  > 체결 반영 > 서버 응답 >  

| Trady 주문 유형 | 외부 체결 이벤트 방향 | 체결 가격 조건 |
|---|---|---|
| 지정가 매수 | 매도 주도 체결 (-) | 외부 체결가 ≤ 지정가 |
| 지정가 매도 | 매수 주도 체결 (+) | 외부 체결가 ≥ 지정가 |
| 시장가 매수 | 매도 주도 체결 (-) | 가격 제한 없음 |
| 시장가 매도 | 매수 주도 체결 (+) | 가격 제한 없음 |

위 체결 규칙에 따른다.


서버의 체결 알림은 SSE로 전달한다. 

### 통식 방식

| 구분 | 통신 방식 | 주요 기능 |
|---|---|---|
| 주문 관리 | REST API | 주문 접수, 주문 취소, 주문 조회 |
| 가상 체결 시스템 | WebSocket | 외부 실시간 체결 이벤트 수신 및 가상 체결 처리 |
| 체결 알림 | SSE | 주문 체결 및 부분 체결 결과 실시간 알림 |
