
# Trady 프로젝트 기능 및 구현 범위 v1

## 1. 문서 목적

본 문서는 Trady 프로젝트의 핵심 기능 네 가지와 각 기능의 구현 범위를 정의한다.

- 주식 차트 조회
- 주식 주문·체결
- D+2 결제
- 계좌 현황

---

## 2. 주식 차트 조회

### 2.1 목적

주식 종목의 가격 변화를 확인할 수 있도록 OHLCV 기반 차트 데이터를 조회하는 기능을 구현한다.

대규모 시계열 데이터를 저장하고 조회하면서 데이터 규모 증가에 따른 조회 성능 문제를 경험하는 것을 목적으로 한다.

### 2.2 관리 데이터

차트 데이터는 국내 주식시장의 종목별 OHLCV 데이터를 기준으로 한다.

기본적으로 다음 데이터를 관리한다.

- 종목
- 기준 시간
- 시가(Open)
- 고가(High)
- 저가(Low)
- 종가(Close)
- 거래량(Volume)

15분봉 데이터를 기본 데이터 단위로 사용한다.

우선 다양한 시간 단위의 봉 데이터를 제공하지 않는다.

### 2.3 구현 기능

다음 기능을 구현한다.

#### 종목별 차트 조회

특정 종목의 OHLCV 데이터를 조회할 수 있다.

#### 기간별 차트 조회

사용자가 요청한 시작 시점과 종료 시점을 기준으로 특정 기간의 차트 데이터를 조회할 수 있다.

#### 대규모 차트 데이터 저장

성능 테스트를 위해 데이터 규모를 단계적으로 증가시킬 수 있도록 대량의 OHLCV 데이터를 구축한다.

최종적으로 약 1,000개 종목의 15분봉 데이터를 기준으로 약 1억 건 규모의 데이터를 구성할 수 있도록 한다.

#### 조회 성능 측정

데이터 규모를 증가시키면서 동일한 조회 조건에 대한 응답시간과 데이터베이스 처리 성능을 측정한다.

성능 문제가 발생하면 원인을 분석하고 필요한 데이터베이스 구조 또는 조회 구조를 적용한 후 동일한 조건에서 다시 측정한다.

## 3. 주식 주문·체결

### 3.1 목적

사용자가 모의 주식 주문을 제출하고 주문 조건에 따라 체결되는 기본적인 주식 거래 과정을 구현한다.

여러 주문이 동시에 발생하는 환경에서 주문가능금액과 보유수량의 데이터 정합성을 유지하고, 주문 처리 과정의 동시성과 성능 문제를 경험하는 것을 목적으로 한다.

또한 주문이 접수되고 호가창에 등록된 후 상대 주문과 체결되는 핵심적인 과정을 단순화하여 구현한다.

### 3.2 주문 유형

다음 두 가지 주문 유형을 구현한다.

#### 지정가 주문

사용자가 원하는 가격과 수량을 지정하여 매수 또는 매도 주문을 제출한다.

지정한 가격 조건을 만족하는 상대 주문이 존재하면 체결하고, 존재하지 않으면 미체결 주문으로 관리한다.

#### 시장가 주문

사용자가 가격을 직접 지정하지 않고 현재 호가창에 존재하는 체결 가능한 상대 주문을 기준으로 거래한다.

### 3.3 주문 처리

주문 요청에 대해 다음 기본 검증을 수행한다.

#### 매수 주문

- 주문가능금액 확인
- 주문 수량 확인
- 주문 가능 여부 판단

#### 매도 주문

- 보유수량 확인
- 주문 수량 확인
- 주문 가능 여부 판단

### 3.4 호가창

체결되지 않은 매수·매도 주문을 관리하기 위한 기본적인 호가창을 구현한다.

호가창에서는 다음 정보를 관리한다.

- 매수 주문
- 매도 주문
- 주문 가격
- 주문 수량
- 미체결 수량
- 주문 접수 순서: 동일한 가격의 주문이 여러 개 존재할 경우 시간 우선 원칙에 따라 먼저 접수된 주문을 우선하여 체결하기 위한 순서를 관리한다.

실제 거래소 수준의 초고성능 호가 시스템을 구현하는 것은 범위에 포함하지 않는다.

### 3.5 주문 매칭

매수 주문과 매도 주문의 가격 및 수량을 비교하여 체결 가능 여부를 판단한다.

다음 규칙을 적용한다.

#### 가격 우선

더 유리한 가격의 주문을 먼저 체결한다.

#### 시간 우선

동일한 가격의 주문이 여러 개 존재하면 먼저 접수된 주문을 우선한다.

#### 부분 체결

주문 전체 수량을 한 번에 체결할 수 없는 경우 체결 가능한 수량만 우선 체결하고 남은 수량은 미체결 상태로 유지한다.

### 3.6 주문 상태

주문 처리 과정에서 최소한 다음 상태를 구분하여 관리한다.

- 주문 접수
- 미체결
- 부분 체결
- 체결 완료
- 주문 실패

### 3.7 동시 주문 처리

동일한 계좌에 여러 주문이 동시에 접근하는 상황을 테스트한다.

다음 문제가 발생하지 않도록 한다.

- 주문가능금액을 초과한 매수
- 보유수량을 초과한 매도
- 동일 주문의 중복 처리
- 주문 처리 중 데이터 불일치
- 재시도로 인한 중복 반영

기본 기능을 구현한 후 동시 주문 규모를 단계적으로 증가시키면서 데이터 정합성과 처리 성능을 측정한다.

## 4. D+2 결제

### 4.1 목적

초기 단계에서는 주문·체결 및 계좌 기능을 우선 구현한 후 기본적인 D+2 결제 배치 기능을 구현한다.

주문 체결 이후 발생하는 결제 예정 데이터를 관리하고 일정 시간이 지난 후 계좌에 반영하는 D+2 결제 과정을 단순화하여 구현한다.

주문 체결 후 생성된 결제 예정 데이터를 관리하고, 결제일(D+2)에 해당 데이터를 일괄 처리하는 과정에서 Batch, Transaction, Retry, Idempotency 및 장애 복구와 관련된 문제를 경험하는 것을 목적으로 한다.

### 4.2 결제 예정 데이터 생성

주문이 체결되면 체결 결과를 기반으로 결제 예정 데이터를 생성한다.

결제 예정 데이터에서는 최소한 다음 정보를 관리한다.

- 계좌
- 체결 정보
- 매수/매도 구분
- 결제 예정 금액
- 체결일
- 결제 예정일
- 결제 처리 상태

### 4.3 D+1 / D+2 결제 예정 금액

계좌에서 체결된 거래를 기준으로 다음 결제 예정 정보를 확인할 수 있도록 한다.

- D+1 결제 예정 금액
- D+2 결제 예정 금액

### 4.4 결제 배치

결제 예정일에 도달한 데이터를 조회하여 계좌에 반영하는 배치 작업을 구현한다.

배치에서는 다음 과정을 수행한다.

결제 대상 조회

→ 결제 처리

→ 계좌 반영

→ 결제 상태 변경

대량의 결제 데이터가 존재하는 상황을 구성하여 배치 처리 결과를 확인한다.

### 4.5 실패 및 재처리

배치 처리 도중 일부 작업이 실패하거나 서버가 중단되는 상황을 고려한다.

재실행 또는 재시도가 발생하더라도 이미 정상적으로 처리된 결제가 다시 반영되지 않도록 한다.

다음 상황을 검증한다.

- 일부 결제 처리 후 작업 중단
- 실패한 결제 재처리
- 동일 배치 재실행
- 동일 결제 중복 처리 요청

최종적으로 재처리 상황에서도 계좌의 데이터 정합성이 유지되어야 한다.

## 5. 계좌 현황

### 5.1 목적

주문·체결 및 D+2 결제 과정에서 변경되는 사용자의 자산 상태를 하나의 계좌를 기준으로 관리한다.

계좌 현황을 통해 주문 → 체결 → 결제 과정의 결과가 사용자 자산에 일관되게 반영되는지 확인한다.

### 5.2 계좌 관리 정보

계좌에서는 다음 정보를 관리한다.

- 현금
- 주문가능금액
- 보유종목
- 보유수량
- 평균매입가
- 평가금액
- 평가손익
- 총자산
- D+1 결제 예정 금액
- D+2 결제 예정 금액

### 5.3 보유종목

체결된 주문을 기준으로 사용자의 보유종목을 관리한다.

각 보유종목에서는 최소한 다음 정보를 관리한다.

- 종목
- 보유수량
- 평균매입가
- 현재가
- 평가금액
- 평가손익

### 5.4 계좌 상태 변경

계좌 상태는 주문·체결·결제 과정과 연결한다.

주문 발생

→ 주문가능금액 및 주문 가능 수량 확인

→ 주문 체결

→ 보유종목 및 결제 예정 정보 변경

→ D+2 결제

→ 결제 결과 계좌 반영

각 과정에서 계좌 상태가 일관되게 유지되는지 검증한다.
