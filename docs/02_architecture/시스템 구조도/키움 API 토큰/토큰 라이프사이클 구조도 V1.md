# 토큰 라이프사이클 구조도 V1

![토큰 라이프사이클 구성도](<토큰 라이프사이클 구조도 V1.png>)

## 구성과 관계

키움 API 토큰 관리는 애플리케이션의 시작·종료 연결, 토큰의 유효성 판단과 보관, 외부 인증 API 호출로 책임을 나눈다. 종목·차트 요청 측은 토큰을 제공받아 사용하며 발급이나 폐기 정책을 직접 관리하지 않는다.



Market API Client는 토큰을 사용하는 측의 역할을 나타낸다. 종목·차트 클라이언트와의 연결은 데이터 수집 구현에서 추가할 대상이다. 화살표는 요청과 의존 방향을 나타내며, 응답은 같은 호출 경로로 돌아온다.

## 하위 구성 요소의 책임

| 구성 요소 | 책임 | 기존 구현과의 연결 |
|---|---|---|
| Token Lifecycle | 애플리케이션 시작·종료 시 토큰 관리 작업을 연결 | `KiwoomTokenLifecycle` |
| Token Provider | 현재 토큰의 유효성 판단, 필요 시 재발급, 동시 접근과 종료 상태 관리 | `KiwoomTokenProvider` |
| Access Token | 토큰 문자열과 만료 시각을 함께 보관하는 값 | `KiwoomAccessToken` |
| Auth Client | 인증 설정으로 외부 API를 호출하고 발급·폐기 응답을 확인 | `KiwoomAuthClient` |

Token Lifecycle은 시작·종료 시점만 연결하고 토큰 만료 여부를 판단하지 않는다. Token Provider가 보관한 토큰을 사용할지 새로 발급할지 결정하며, Auth Client는 그 결정에 따른 외부 통신을 담당한다. Access Token은 별도 저장소나 실행 모듈이 아니라 Token Provider가 메모리에 보관하는 값이다.

## 시작 시 토큰 준비

### 1. Token Lifecycle → Token Provider

- 애플리케이션이 시작되면 Token Lifecycle이 토큰 초기화를 요청한다.
- Token Provider는 종료 상태인지 확인하고, 보관한 토큰이 있는지 확인한다.
- 보관한 토큰이 없으면 발급 과정으로 진행한다.

### 2. Token Provider → Auth Client → Kiwoom REST API

- Token Provider가 Auth Client에 토큰 발급을 요청한다.
- Auth Client는 인증 설정을 사용하여 키움 인증 API에 발급을 요청한다.
- 발급 응답의 성공 여부와 토큰 존재 여부를 확인한다.
- 요청이나 응답 검증에 실패하면 초기화 요청 측으로 실패를 전파한다.

### 3. Auth Client → Token Provider → Access Token

- Auth Client가 확인한 발급 응답을 Token Provider에 전달한다.
- Token Provider는 만료 시각을 해석하고 남은 유효 시간이 1분보다 많은지 확인한다.
- 유효 시간이 부족하면 초기화 실패를 전파한다.
- 검증을 통과하면 토큰과 만료 시각을 Access Token으로 묶어 메모리에 보관한다.

### 4. Token Provider → Token Lifecycle

- 토큰 준비가 성공하면 초기화 요청이 완료된다.
- 초기화가 실패하면 Token Lifecycle로 실패가 전파된다.
- 토큰을 준비하지 못한 상태를 초기화 완료로 처리하지 않는다.

## 사용 중 토큰 제공과 재발급

현재 구조는 토큰을 요청받을 때 만료 여부를 판단한다. 서버가 실행 중이어도 토큰 요청이 없으면 재발급이 실행되지 않는다. 만료 전에 독립적으로 갱신하는 모듈이 필요하다.

### 1. Market API Client → Token Provider

- 종목·차트 요청 측이 사용할 토큰을 요청한다.
- Token Provider가 종료 상태이면 요청을 거절한다.
- 토큰 제공과 폐기는 같은 동기화 경계 안에서 처리한다.

### 2. Token Provider → Access Token

- 보관한 토큰과 만료 시각을 확인한다.
- 만료까지 1분보다 많이 남았으면 보관한 토큰을 사용한다.
- 토큰이 없거나 만료까지 1분 이하로 남았으면 재발급 과정으로 진행한다.
- 1분의 여유 시간은 외부 요청 도중 만료될 가능성을 줄이기 위한 값이며, 요청 완료를 보장하지는 않는다.

### 3. Token Provider → Auth Client → Kiwoom REST API

- 필요할 때 새 토큰 발급을 요청한다.
- 별도의 주기적 갱신 작업 없이 토큰 요청 시점에 재발급 여부를 판단한다.
- refresh token을 사용하는 갱신 방식은 아니다.
- 발급이 실패하면 토큰 요청 측에 실패를 전달한다.

### 4. Auth Client → Token Provider → Access Token

- 발급 응답의 만료 시각과 남은 유효 시간을 확인한다.
- 남은 유효 시간이 1분보다 많으면 현재 토큰을 새 값으로 교체한다.
- 교체 과정에서 이전 토큰의 원격 폐기를 별도로 요청하지 않는다.
- 새 토큰의 검증이 실패하면 사용할 토큰을 제공한 것으로 처리하지 않는다.

### 5. Token Provider → Market API Client

- 보관한 유효 토큰 또는 검증을 통과한 새 토큰을 제공한다.
- 요청 측은 제공받은 토큰을 종목·차트 API 호출에 사용한다.

## 종료 시 토큰 폐기

### 1. Token Lifecycle → Token Provider

- 애플리케이션 정상 종료 시 보관한 토큰의 폐기를 요청한다.
- Token Provider는 종료 상태로 전환해 새로운 토큰 요청을 거절한다.
- 보관한 토큰이 없으면 외부 폐기 요청 없이 처리를 마친다.
- 강제 종료나 전원 차단에서는 정상 종료 처리가 실행되지 않을 수 있다.

### 2. Token Provider → Auth Client → Kiwoom REST API

- 보관한 토큰이 있으면 Auth Client에 폐기를 요청한다.
- Auth Client가 키움 인증 API에 원격 폐기를 요청하고 성공 여부를 확인한다.
- 현재 자동 재시도는 없다.

### 3. Auth Client → Token Provider → Access Token

- 원격 폐기가 성공하면 메모리에서 현재 토큰을 제거한다.
- 원격 폐기가 실패하면 보관한 값은 제거하지 않고 종료 상태를 유지한다.
- 메모리 값이 사라지는 것과 원격 토큰 폐기는 서로 다른 동작이다.
- 프로세스가 종료됐다는 사실만으로 원격 토큰이 폐기됐다고 판단하지 않는다.

### 4. Token Provider → Token Lifecycle

- 폐기 실패는 Token Lifecycle로 전달되며 경고를 남긴다.
- 현재 Lifecycle은 실패 이후에도 폐기 완료 로그를 출력한다.
- 이 로그는 원격 폐기 성공을 의미하지 않으며, 수집 모드 연결 시 성공·실패 표현을 조정한다.

## 향후 갱신 모듈과 종료 동작의 분리

아래는 향후 개선할 관계이며 현재 PNG와 구현에 포함된 구성 요소를 뜻하지 않는다. [토큰 관리 구조와 후속 개선 계획](<../../../work-plan/backend/2026-10-10 키움 API 토큰 관리 구조와 후속 개선 계획.md>)의 후속 작업 TODO로 관리한다.

### 1. Token Renewal Module → Token Provider

- 운영 중 만료 전에 갱신을 요청하는 별도 모듈을 추가한다.
- 갱신 모듈은 갱신 시점을 결정하고, Token Provider는 발급·검증·교체를 담당한다.
- 요청 시점의 갱신과 별도 모듈의 갱신이 겹쳐도 중복 발급하지 않도록 같은 관리 경계로 연결한다.
- 갱신은 서버 종료 상태로 전환하지 않는다. 갱신 주기와 실패 후 재시도 정책은 추후 결정한다.

### 2. Token Provider → Auth Client → Kiwoom REST API

- 새로 발급받은 토큰의 유효성을 확인한 뒤 현재 토큰을 교체하는 구조를 기본으로 검토한다.
- 재발급 시 동일한 토큰을 반환하는지, 이전 토큰이 유지되는지 또는 무효화되는지 공식 자료와 제한된 실제 요청으로 먼저 확인한다.
- 서로 다른 토큰이 발급된다면 이전 토큰 폐기가 새 토큰에도 영향을 주는지 확인한다.
- 이 정책을 확인하기 전에는 운영 중 갱신에 기존 토큰의 원격 폐기를 추가하지 않는다.
- 이전 토큰을 따로 폐기해야 한다면 진행 중 요청의 사용 여부와 폐기 실패 처리를 함께 설계한다. 새 토큰과 같은 값을 폐기하지 않도록 한다.

### 3. Token Lifecycle → Token Provider

- 정상 종료 시 새 수집 작업을 차단하고 진행 중 요청을 정리한 뒤 종료 전용 폐기를 호출하는 구조로 연결한다.
- 종료 전용 동작만 종료 상태 전환과 현재 토큰 폐기를 담당한다.
- 현재 폐기 동작은 종료 상태로 전환하므로 운영 중 갱신에 그대로 재사용하지 않는다.
- 종료 시 갱신 모듈의 신규 실행도 중단하여 폐기와 재발급이 경합하지 않도록 한다.

## 책임을 분리한 이유

| 분리한 책임 | 얻는 효과 |
|---|---|
| 시작·종료 연결과 토큰 관리 | 실행 모드의 시작·종료 정책을 바꿔도 토큰 유효성 판단을 다시 구현할 필요가 없다. |
| 토큰 관리와 인증 통신 | 외부 인증 요청 형식이 바뀌면 Auth Client를 조정하고, 갱신 정책이 바뀌면 Token Provider를 조정할 수 있다. |
| 토큰 사용과 토큰 발급 | 종목·차트 클라이언트가 동일한 토큰 관리 정책을 사용하며 각각 만료 처리를 구현하지 않는다. |
| 토큰 문자열과 만료 시각의 결합 | 현재 보관한 토큰의 만료 시각을 같은 값으로 다루어 유효성 판단에 사용한다. |

Token Provider의 토큰 제공과 폐기는 같은 동기화 경계 안에서 처리한다. 여러 스레드가 동시에 만료를 확인해 중복 발급하는 상황과, 폐기 중 새 토큰을 발급하는 상황을 줄인다. 이 보호 범위는 하나의 애플리케이션 인스턴스이며 여러 프로세스 사이의 발급 경쟁까지 제어하지는 않는다.


수집 종료는 새 작업 시작 차단 → 진행 중 작업 정리 → 토큰 폐기 → 프로세스 잠금 해제 순서로 연결한다. 
이미 폐기한 Token Provider는 종료 상태를 유지하므로 다음 수집 회차에 그대로 재사용할 수 없다.

실행 모드와 수집 프로세스 잠금은 토큰 자체의 유효성 판단과 별도의 책임이다. 이 연결 방향은 [종목 정보 동기화와 과거 캔들 적재 및 차트 조회 계획](<../../../work-plan/backend/2026-10-10 종목 정보 동기화와 과거 캔들 적재 및 차트 조회.md>)을 기준으로 하며, 현재 코드에 모두 적용된 구조를 뜻하지 않는다.
