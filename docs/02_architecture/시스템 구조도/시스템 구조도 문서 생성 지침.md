# 구조도 문서 생성 지침

## 문서의 목적

구조도 문서는 시스템의 구성 요소, 하위 모듈의 계층과 책임, 구성 요소 사이의 처리 흐름, 해당 구조를 선택한 이유를 설명한다. 이후 설계를 다시 살펴볼 때 당시의 목적과 선택 근거를 이해할 수 있도록 작성한다.

그림은 큰 구성과 연결 관계를 표현하고, 마크다운 본문은 그림에서 생략한 하위 책임과 구간별 처리 과정을 설명한다. 작업 순서·수정 파일·검증 계획은 `docs/work-plan/`의 사용자용 작업 계획에서 다룬다.

이미지의 디자인과 표현 방식은 [시스템 구성도 생성 지침](<시스템 구성도 이미지 생성 지침 .docx>)을 따른다. 이 문서는 이미지와 함께 작성하는 마크다운 문서의 양식을 정의한다.

## 저장 위치와 버전

- 프로젝트 루트의 `docs/02_architecture/시스템 구조도/` 아래 설계 대상별 폴더에 저장한다.
- 문서명은 `{설계 대상} 구조도 V{번호}.md`, 이미지명은 같은 대상과 버전의 `.png`로 구성한다.
- 기존 파일명과 폴더명을 우선적으로 따른다. 문서명과 이미지명의 띄어쓰기·기호가 다른 경우 실제 이미지명을 링크에 사용한다.
- 구조가 변경되어 버전을 올릴 때 이전 버전의 문서와 이미지는 보존하고 새 버전을 작성한다.
- 이전 버전과 현재 버전은 같은 설계 대상 폴더에서 관리한다.
- 이미지와 관련 문서는 상대 경로로 연결한다. 공백이 포함된 링크 경로는 `<...>`로 감싼다.

## 공통 문서 순서

다음 순서로 작성한다. 처리 흐름의 제목과 개수는 설계 대상에 맞게 정하되, 구성과 책임을 설명한 뒤 흐름을 설명하는 순서를 유지한다.

| 순서 | 항목 | 작성 기준 |
|---|---|---|
| 1 | 제목과 PNG | 설계 대상과 버전을 제목에 적고 같은 버전의 이미지를 연결 |
| 2 | 이전 버전에서 보완할 부분 | V2 이상에서 직전 버전의 한계와 보완 구조 설명 |
| 3 | 구성과 관계 | 시스템 경계, 상위·하위 계층, 주요 의존 관계 설명 |
| 4 | 하위 구성 요소의 책임 | 구성 요소별 상위 영역과 책임을 표로 정리 |
| 5 | 기능별 처리 흐름 | 구간별 번호 제목 아래 처리 과정을 목록으로 설명 |
| 6 | 책임을 분리한 이유 | 처음 정의한 구조의 분리 근거 설명. 버전 변경 이유와 중복되면 그 항목에서 함께 설명 |
| 7 | 구조의 경계와 관련 설계 | 필요한 경우 실행 모드·적용 범위·향후 설계를 구분하고 관련 문서 연결 |

V1에는 이전 버전 비교 항목을 만들지 않는다. 구성·책임·처리 흐름과 책임 분리 이유를 작성한다. V2 이상에서는 이전 버전에서 보완할 부분을 생략하지 않는다.

## 이전 버전에서 보완할 부분

- 제목은 `## V{직전 번호}에서 보완할 부분`으로 작성한다. V3 문서에서는 V2와 비교한다.
- 직전 버전 문서를 링크하고 유지하는 설계 원칙을 먼저 설명한다.
- 부족했던 책임, 계층, 연결 관계나 새 요구사항을 구체적으로 설명한다.
- `이전 버전에서 부족했던 부분 | 현재 버전에서 보완하는 구조` 형식의 표로 변경 관계를 정리한다.
- 이전 설계에 없던 책임을 구현 결함으로 단정하지 않는다. 요구사항이 확장된 경우 그 배경을 설명한다.

## 구성과 하위 책임

### 구성과 관계

- 시스템 안과 밖에 어떤 구성 요소가 있는지 설명한다.
- 상위 영역이 포함하는 하위 모듈과 동일 계층의 구성 요소를 구분한다.
- 포함 관계와 실행 선후 관계를 혼동하지 않는다. 먼저 호출된다고 상위 모듈이 되는 것은 아니다.
- 논리적 모듈을 독립 서버나 배포 단위로 해석할 가능성이 있으면 그 경계를 설명한다.
- 그림과 본문에서 같은 구성 요소는 같은 이름을 사용한다.

### 하위 구성 요소의 책임

- 기본 표는 `구성 요소 | 상위 영역 | 책임`으로 작성한다.
- 계층이 단순하여 상위 영역을 반복할 필요가 없다면 `구성 요소 | 책임`으로 작성할 수 있다.
- 구현과의 대응이 필요한 문서는 참조용 열을 추가할 수 있지만, 아직 정하지 않은 클래스나 메서드를 확정하지 않는다.
- 하나의 요소가 무엇을 담당하고 다른 요소에 무엇을 맡기는지 설명한다.
- 모듈 내부의 변환·검증·저장처럼 역할을 구분하는 수준까지 작성하고, 코드·메서드 호출·SQL·DTO·테이블 컬럼을 나열하지 않는다.

## 처리 흐름 작성 양식

처리 목적별로 `## 시작 시 토큰 준비`, `## 종목 기본 정보 동기화`와 같은 제목을 사용한다. 각 흐름 안에서는 구간마다 번호가 있는 `###` 제목을 사용하고, 그 아래 처리 과정을 목록으로 작성한다.

### 구간 제목

- 기본 형식은 `### 1. 구성 요소 A → 구성 요소 B`다.
- 짧은 외부 호출 경로를 함께 표현할 때는 `### 2. 구성 요소 B → 외부 연동 요소 → 외부 API`처럼 작성한다.
- 모듈 내부의 하위 책임은 `### 2. 모듈명: Parsing / Mapping → Validation`처럼 모듈 소속을 명시한다.
- 각 기능별 흐름의 번호는 1부터 시작하고 연속으로 작성한다.
- 요청 경로와 반환 경로는 필요할 때 각각의 구간 제목으로 설명한다.

### 구간 아래 과정 목록

- 어떤 계기로 요청하는지, 다음 요소에 무엇을 전달하는지, 해당 구간에서 무엇을 판단하거나 처리하는지 적는다.
- 다음 단계로 진행하는 조건이나 처리 실패가 흐름에 미치는 영향이 중요하면 함께 적는다.
- 분기, 반복, 재실행, 종료 동작은 실제 설계에 있는 경우에만 설명한다.
- 코드 수준의 세부 구현보다 모듈의 책임과 데이터 이동이 드러나게 작성한다.
- 예상 동작을 실제 실행 결과처럼 표현하거나 테스트 통과 여부를 기록하지 않는다.

작성 예시는 다음과 같다.

### 1. Token Lifecycle → Token Provider

- 애플리케이션이 시작되면 토큰 초기화를 요청한다.
- 보관한 토큰의 존재와 유효성을 확인한다.
- 새 토큰이 필요하면 인증 요청을 담당하는 구성 요소로 발급을 요청한다.

이 형식을 토큰에만 한정하지 않고 수집·저장·조회 등 각 설계의 흐름에도 적용한다.

## 현재 구조와 향후 설계

- 현재 구조와 향후 추가할 모듈은 구분해서 설명한다.
- 향후 모듈은 별도의 `## 향후 ...` 항목에 두고 현재 그림에 포함된 요소처럼 표현하지 않는다.
- 외부 정책이나 실측이 필요한 결정은 확인할 사항과 그 결과에 따라 정할 책임을 적는다.
- 상세 후속 개선 과제는 관련 `docs/work-plan/` 문서에 연결한다.
- 다른 구조도에서 관리하는 책임은 요약과 링크로 연결하고 상세 설명을 중복하지 않는다.
- 설계와 코드가 다르면 차이를 설명한다. 문서를 작성하기 위해 구현을 임의로 변경하지 않는다.

## 작성 후 확인

- 그림과 문서의 대상·버전·구성 요소 이름이 일치하는지 확인한다.
- 이미지와 이전 버전, 관련 설계·작업 계획 링크가 실제 파일을 가리키는지 확인한다.
- 버전 변경 문서에 직전 버전의 한계와 변경 이유가 있는지 확인한다.
- 구성·하위 책임·구간별 흐름이 같은 설계를 설명하는지 확인한다.
- 구간 번호와 제목의 화살표 방향이 처리 과정과 일치하는지 확인한다.
- 수행 상태·실행 결과·완료 보고, 코드 구현 계획이 구조 설명에 섞이지 않았는지 확인한다.
- 문서 생성 지시나 작성 기준 자체를 실제 구조도 본문에 복사하지 않는다.
