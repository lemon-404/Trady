# 차트 데이터 수집·조회 구조도 V2

![차트 데이터 수집·조회 구성도 V2](<차트 데이터 수집 조회 구조도 V2.png>)

## V1에서 보완할 부분

[V1](<차트 데이터 수집·조회 구조도 V1.md>)은 외부 차트 응답을 변환·검증하여 저장하는 흐름과, 저장된 차트를 조회하는 흐름을 분리했다. V2에서도 이 책임 분리를 유지한다. 동일한 DB 데이터와 조회 조건으로 성능을 측정하여 외부 API의 응답 시간이나 호출 제한이 조회 성능 측정에 섞이지 않도록 한다.

다만 V1의 단일 차트 수집 흐름만으로는 다음 관계가 드러나지 않는다.

| V1에서 부족했던 부분 | V2에서 보완하는 구조 |
|---|---|
| 차트 데이터 외에 종목명·시장 정보를 확보하는 흐름이 없음 | 종목 기본 정보 동기화와 과거 캔들 적재를 별도 하위 모듈로 구분 |
| 종목 정보를 준비한 뒤 해당 종목의 캔들을 적재하는 순서가 없음 | Sync Coordinator가 종목 동기화 → 캔들 적재 순서를 조율 |
| 수집을 언제 시작하고 반복할지 표현하지 않음 | 즉시 실행과 주기 실행이 같은 동기화 흐름을 사용하도록 구성 |
| 인증과 토큰 관리의 의존 관계가 없음 | Market API Client와 Token Manager의 관계를 명시 |
| 조회할 데이터가 OHLCV 중심으로만 표현됨 | 종목 기본 정보와 저장된 캔들을 함께 조회 |
| 외부 API 제약에 따라 수집 대상을 제한하는 기준이 없음 | 선정한 종목·봉 주기·과거 기간 안에서 동기화하도록 설계 |

V1이 종목·인증 책임을 구체화하기 전의 차트 처리 흐름이었다면, V2는 실제 외부 API 연동과 반복 수집에 필요한 책임을 추가한 구조다.

### 실행 조율과 개별 수집 책임 분리

즉시 실행과 주기 실행은 실행 계기가 다르지만 한 회차의 동기화 순서는 같다. Sync Coordinator가 실행 순서를 담당하고 각 수집 모듈은 자신의 데이터만 처리한다. 따라서 반복 실행을 추가해도 종목·캔들 처리 흐름을 각각 다시 구현하지 않는다.

### 외부 통신과 내부 데이터 처리 분리

Market API Client는 외부 요청과 응답 수신을 담당하고, 종목·캔들 모듈은 내부 형식으로의 변환·검증·저장을 담당한다. 외부 요청 규격이나 인증 방식이 바뀌는 경우와 데이터 검증·저장 정책이 바뀌는 경우를 독립적으로 다룰 수 있다.

### 수집과 조회 분리 유지

Chart Query API는 저장된 종목 정보와 캔들을 조회한다. 데이터가 없는 구간을 조회하더라도 외부 수집을 자동으로 실행하지 않는다. 외부 API가 실패하거나 수집이 진행 중이어도 저장된 데이터는 조회할 수 있으며, 수집량과 조회 성능을 각각 검증할 수 있다.

## 구성과 관계

Trady Backend의 Market Data Module은 종목 정보와 과거 캔들을 수집·저장하고, Chart Query API는 같은 PostgreSQL에 저장된 데이터를 조회한다. Kiwoom REST API와 Client는 백엔드 경계 밖에 위치한다.

Market Data Module 안에서 Sync Coordinator는 실행을 조율하고 Stock Sync Module과 Historical Candle Module은 각각 종목 정보와 캔들을 처리한다. 두 하위 모듈은 Market API Client를 통해 외부 데이터를 요청하며, Market API Client는 Token Manager에서 인증 토큰을 제공받는다.

모듈은 논리적인 책임의 경계다. 각 모듈을 독립 서버나 별도 배포 단위로 나누는 구조를 뜻하지 않는다. 화살표는 요청·의존 방향을 나타내며 응답은 같은 호출 경로로 돌아온다.

## 하위 구성 요소의 책임

| 구성 요소 | 상위 영역 | 책임 |
|---|---|---|
| Sync Coordinator | Market Data Module | 즉시·주기 실행 연결과 종목 → 캔들 순서 조율 |
| Stock Sync Module | Market Data Module | 선정 종목의 기본 정보 변환·검증·동기화 |
| Historical Candle Module | Market Data Module | 선정 종목의 과거 캔들 수집·변환·검증·저장 |
| Market API Client | Market Data Module | 종목·차트 요청, 응답과 연속 조회 정보 수신, 요청 간격 관리 |
| Token Manager | Market Data Module | 외부 요청에 사용할 토큰의 유효성 판단·재발급·종료 시 폐기 |
| Chart Query API | Trady Backend | 조회 조건 확인과 저장된 종목 정보·캔들 제공 |
| PostgreSQL | Trady Backend | 종목 기본 정보와 과거 캔들 보관 |

Stock Sync Module과 Historical Candle Module은 같은 계층에 위치하며 실행 선후 관계를 가진다. 변환·검증·저장은 각 모듈 안의 하위 책임으로 두고, 클래스나 메서드 배치는 이 문서에서 확정하지 않는다.

## 동기화 시작과 실행 조율

### 1. 즉시·주기 실행 → Sync Coordinator

- sync 모드는 한 회차의 동기화를 즉시 실행한다.
- scheduler 모드는 즉시 한 회차를 수행한 뒤 같은 동기화 흐름을 반복한다.
- 실행 계기가 달라도 종목 정보 준비 후 캔들을 적재하는 순서를 사용한다.
- 제공 종목·봉 주기·과거 기간과 반복 간격은 API 실측 후 결정한다.

### 2. Sync Coordinator → Stock Sync Module

- 선정 종목의 기본 정보 동기화를 요청한다.
- 종목 정보를 준비한 뒤 해당 종목에 캔들을 연결할 수 있도록 한다.
- 종목 동기화가 완료되기 전에는 과거 캔들 적재를 시작하지 않는다.

### 3. Sync Coordinator → Historical Candle Module

- 종목 동기화가 끝나면 준비된 종목을 대상으로 캔들 적재를 요청한다.
- 개별 모듈의 처리 완료와 실패를 조율한다.
- 데이터 변환·검증·저장 자체는 각 하위 모듈에 맡긴다.

## 종목 기본 정보 동기화

### 1. Stock Sync Module → Market API Client → Kiwoom REST API

- 선정 종목의 기본 정보를 요청한다.
- Market API Client는 외부 요청과 응답 수신을 담당한다.
- Stock Sync Module에 종목 응답을 전달한다.

### 2. Stock Sync Module: Parsing / Mapping → Validation

- Parsing / Mapping은 외부 종목 응답을 내부 종목 정보로 변환한다.
- Validation은 종목을 식별하고 저장하는 데 필요한 정보를 확인한다.
- 검증한 종목 정보만 저장 책임으로 전달한다.

### 3. Stock Sync Module: Validation → Storage → PostgreSQL

- Storage는 신규 종목 정보를 저장하고 기존 종목 정보를 갱신한다.
- 기존 종목의 식별 관계를 유지하면서 이름·시장 정보를 갱신한다.
- 캔들 수집이 사용할 종목 정보를 준비한다.

### 4. Stock Sync Module → Sync Coordinator

- 종목 동기화가 끝나면 과거 캔들 수집을 시작할 수 있도록 연결한다.
- 종목 정보 준비와 캔들 적재의 실행 순서를 유지한다.

## 과거 캔들 수집과 적재

### 1. Historical Candle Module: Collection → Market API Client → Kiwoom REST API

- Collection은 선정 종목·봉 주기·기간에 맞는 차트 데이터를 요청한다.
- Market API Client는 외부 차트 요청과 응답 수신, 연속 조회 정보를 담당한다.
- Collection은 수집 범위와 다음 페이지를 요청할지를 판단한다.

### 2. Historical Candle Module: Collection → Parsing / Mapping

- 수집한 외부 차트 응답을 변환 책임으로 전달한다.
- 가격·시각·거래량을 내부 OHLCV 형식으로 변환한다.
- 외부 응답 형식과 내부 저장 형식의 차이를 이 경계에서 처리한다.

### 3. Historical Candle Module: Parsing / Mapping → Validation

- 변환한 캔들의 필수 정보와 값의 관계를 검증한다.
- 저장 가능한 캔들인지 확인하고 검증한 데이터를 저장 책임으로 전달한다.

### 4. Historical Candle Module: Validation → Storage → PostgreSQL

- Storage는 캔들을 해당 종목과 연결해 저장한다.
- 설정된 과거 기간을 다시 수집하면 기존 캔들은 갱신하고 없는 캔들은 추가한다.
- 같은 캔들이 반복 수집되어도 중복 행을 만들지 않도록 한다.
- V1의 변환·검증·저장 책임은 Historical Candle Module 안에서 유지한다.

### 5. Historical Candle Module → Sync Coordinator

- 수집·적재가 끝나면 해당 회차를 마무리하도록 연결한다.
- 개별 수집 모듈의 실패를 전체 동기화가 성공한 것으로 처리하지 않는다.
- 주기 실행에서는 같은 종목 → 캔들 흐름을 다음 회차에도 사용한다.

## 외부 요청과 토큰 관리

Token Manager는 Token Lifecycle·Token Provider·Auth Client를 묶어 표현한 논리적 역할이다. 아래 흐름은 수집 기능에 연결할 목표 구조를 설명한다.

### 1. Market API Client → Token Manager

- 외부 종목·차트 요청에 사용할 토큰을 Token Provider에 요청한다.
- Token Provider는 남은 유효기간을 확인하고, 갱신이 필요한 경우 갱신한 뒤 보관 토큰을 제공한다.
- 종목·캔들 처리 모듈이 각각 인증 정책을 관리하지 않도록 한다.

### 2. Token Provider → Auth Client → Kiwoom REST API

- 토큰 발급·폐기 요청은 Auth Client를 통해 전달한다.
- 갱신 시 남은 유효기간에 따라 폐기 후 발급 또는 발급 후 교체를 수행한다.
- 데이터 요청과 인증 요청의 책임을 구분한다.

토큰의 기본 구성과 라이프 사이클은 [토큰 라이프사이클 구조도 V1](<../키움 API 토큰/토큰 라이프사이클 구조도 V1.md>)을 참고한다. 운영 중 갱신 정책은 [키움 API 토큰 관리 구조](<../../../work-plan/backend/2026-10-10 키움 API 토큰 관리 구조.md>)를 기준으로 한다.

## 차트 데이터 조회

### 1. Client → Chart Query API: Query Validation

- Client가 조회할 종목·봉 주기·기간을 전달한다.
- Query Validation은 제공 범위와 조회 조건을 확인한다.
- 조회 요청이 Market Data Module의 수집을 실행하지 않도록 한다.

### 2. Chart Query API: Query Validation → Data Query → PostgreSQL

- 검증한 조건으로 저장된 종목 기본 정보와 캔들을 조회한다.
- Market Data Module과 같은 PostgreSQL을 사용한다.
- 데이터가 없는 구간에서도 외부 API를 호출하거나 자동 수집을 시작하지 않는다.

### 3. Chart Query API: Data Query → Response Mapping → Client

- Response Mapping은 조회한 종목 정보와 캔들을 응답으로 구성한다.
- Client에 저장된 차트 데이터를 반환한다.
- 외부 API 응답을 기다리는 과정이 조회 흐름에 포함되지 않도록 한다.

## 실행 방식과 구조의 경계

| 모드 | 활성화하는 흐름 |
|---|---|
| api | Chart Query API를 통한 DB 조회 |
| sync | 종목 동기화와 과거 캔들 적재를 즉시 한 번 수행 |
| scheduler | 즉시 한 회차 수행 후 같은 동기화 흐름을 주기적으로 반복 |

전체 종목과 모든 과거 데이터를 수집한다는 전제는 두지 않는다. WebSocket 실시간 수신과 실시간 봉 집계는 향후 별도 책임으로 추가할 대상이며, 과거 캔들의 주기적 수집을 실시간 수신으로 취급하지 않는다.

세부 구현 순서와 변경 파일은 [종목 정보 동기화와 과거 캔들 적재 및 차트 조회 계획](<../../../work-plan/backend/2026-10-10 종목 정보 동기화와 과거 캔들 적재 및 차트 조회.md>)에서 다룬다.
