# 1. Prototype 단계

프로토타입은 **최적화되지 않았지만 전체 기능이 정상적으로 연결되는 최초 버전**을 목표로 한다.

```text
차트 조회

주문
 ↓
체결
 ↓
결제 예정
 ↓
D+2 결제
 ↓
계좌
```

이 단계에서는 Redis, 파티셔닝, 복잡한 Lock 등의 최적화 기술을 미리 적용하지 않는다.

작은 규모에서 정확하게 동작하는 시스템을 먼저 구현한 후 규모를 확대하는 것이 프로젝트의 기본 방향이다. 프로젝트 배경 및 추진 목적 v1

### Prototype 완료 기준

**① 핵심 기능 기본 구현**

차트 조회 / 주문·체결 / D+2 / 계좌가 실제 DB를 기반으로 동작한다.

**② 회귀 테스트 구축**

이후 코드와 구조가 변경되더라도 기존 비즈니스 결과와 데이터 정합성이 유지되는지 검증할 수 있는 테스트를 만든다.

**③ 성능 테스트 구축**

동일한 조건으로 반복 측정할 수 있는 성능 테스트 환경을 구성한다.

**④ Baseline 측정**

최적화되지 않은 Prototype v0의 최초 성능을 기록한다.

# 2. 테스트는 두 가지로 운영

### 회귀 테스트 — Regression Test

목적은:

> **구현 구조를 변경하더라도 기존 기능과 결과가 변하지 않았는지 검증한다.**

다음 내용을 포함한다.

```text
정상 기능
예외 처리
데이터 정합성
멱등성
주문 → 체결 → 결제 → 계좌 전체 흐름
```

구조를 개선할 때마다 가장 먼저 회귀 테스트를 실행한다.

### 성능 테스트 — Performance Test

목적은:

> **구조 변경 전후의 성능 변화를 동일한 조건에서 수치로 비교한다.**

주요 측정 항목은 프로젝트에서 정의한 지표를 따른다. 추진 성과 및 기대효과 v1

```text
TPS / RPS
AVG
P95
P99
오류율

DB 처리시간
DB Connection
Lock 경합

CPU
Memory

데이터 정합성
```

# 3. 개선 단계의 핵심 원칙

**문제가 발생했다고 바로 특정 기술을 적용하지 않는다.**

반드시 다음 과정을 거친다.

```text
규모 확대
    ↓
문제 재현
    ↓
문제 수치화
    ↓
원인 분석
    ↓
가능한 개선 방법 조사
    ↓
여러 개선 방법 학습
    ↓
각 방법의 장단점 / Trade-off 비교
    ↓
현재 문제에 가장 적합한 방법 선정
    ↓
선택 이유 작성
    ↓
구조 개선
    ↓
회귀 테스트
    ↓
성능 테스트
    ↓
개선 전후 비교
```

즉,

> **“이 문제가 발생했고 A/B/C 방법을 검토했으며, 각각 이러한 장단점이 있었다. 현재 조건에서는 B가 가장 적절하다고 판단하여 B를 선택했다.”**

가 되어야 한다.

이것이 프로젝트에서 이미 정한 **현재 시스템의 한계를 먼저 측정하고 필요한 기술을 선택한다**는 방향과도 일치한다. 프로젝트 배경 및 추진 목적 v1

# 4. 모든 개선 결과는 AS-IS / TO-BE 형태로 정리

그리고 **각 개선 과정의 최종 기록은 AS-IS / TO-BE 형태로 통일한다.**

## AS-IS

현재 시스템의 상태와 문제를 기록한다.

```text
[AS-IS]

구조
- 현재 구현 구조

테스트 조건
- 데이터 규모
- 동시 사용자
- 요청 수

측정 결과
- TPS
- P95
- P99
- 오류율

문제
- 어떤 문제가 발생했는가

원인
- 왜 문제가 발생했는가
```

## 개선안 검토

AS-IS와 TO-BE 사이에는 반드시 **대안 검토 과정**을 기록한다.

| 개선 후보 | 장점 | 단점 | 적합성 |
|---|---|---|---|
| 방법 A | ... | ... | △ |
| 방법 B | ... | ... | ◎ |
| 방법 C | ... | ... | ○ |

그리고 선택 이유를 작성한다.

```text
선택: 방법 B

선택 이유

현재 병목의 직접적인 원인을 해결할 수 있으며,
방법 A보다 현재 데이터 규모에서 적합하고,
방법 C보다 시스템 복잡도를 적게 증가시키기 때문에
방법 B를 선택한다.
```

**선택 이유를 작성한 이후에 실제 구현을 수정한다.**

## TO-BE

개선하려는 구조를 정의한다.

```text
[TO-BE]

변경 구조
- 어떤 구조로 변경할 것인가

변경 사항
- 어떤 부분을 수정할 것인가

목표
- 어떤 문제를 해결할 것인가
- 어느 정도의 성능을 목표로 하는가
```

그리고 구현 후 실제 결과까지 붙인다.

```text
[검증 결과]

회귀 테스트
PASS

성능 테스트

           AS-IS       TO-BE 적용 후

TPS          500           850
P95        800ms         250ms
P99       1,200ms        400ms
오류율       0%             0%

결론
- 성능이 어느 정도 개선되었는가
- 왜 개선되었는가
- 새로운 Trade-off는 무엇인가
- 추가 개선이 필요한가
```

즉, **TO-BE는 목표 구조이고 `TO-BE 적용 후 결과`는 실제 측정 결과**로 구분한다.

이걸 **프로젝트 전체의 공통 개발 원칙**으로 잡으면 돼.

특히 나중에 포트폴리오에서도 기능별로 **`AS-IS → 문제/원인 → 대안 비교 → 선택 근거 → TO-BE → 회귀 검증 → 성능 검증 → 결과`**라는 동일한 구조로 정리할 수 있어서, 단순히 *“인덱스, Redis, Lock을 사용해봤다”*가 아니라 **어떤 문제를 어떤 근거로 해결했는지를 보여주는 프로젝트**가 된다.
