

## Trady Prototype v0 구현 범위

프로토타입에서는 차트 조회, 주문·체결, D+2 결제, 계좌 현황의 네 가지 핵심 기능을 단순한 구조로 구현한다. 각 기능을 실제 데이터베이스와 연결하고 주문부터 결제 및 계좌 반영까지의 전체 거래 흐름이 정상적으로 동작하도록 한다.

프로토타입 구현 이후 회귀 테스트를 통해 기능과 데이터 정합성을 검증하고, 성능 테스트를 통해 최초 시스템의 성능 Baseline을 측정한다.

### 1. 주식 차트 조회

종목별 OHLCV 데이터를 데이터베이스에 저장하고 조회할 수 있도록 구현한다.

사용자가 종목과 조회 시작 시점 및 종료 시점을 입력하면 해당 기간의 OHLCV 데이터를 조회하여 반환하도록 구현한다.

```text
종목
 ↓
OHLCV 데이터 저장
 ↓
종목 + 시작 시점 + 종료 시점 입력
 ↓
기간별 OHLCV 데이터 조회
 ↓
조회 결과 반환
```

프로토타입 단계에서는 테스트에 필요한 소규모 차트 데이터를 구축한다.

대규모 데이터 구축과 인덱스, 복합 인덱스, 파티셔닝, 캐시 등의 조회 성능 개선은 이후 데이터 규모를 단계적으로 확대하면서 진행한다.

---

### 2. 주식 주문·체결

사용자가 매수 또는 매도 주문을 제출할 수 있도록 구현한다.

매수 주문에서는 주문가능금액과 주문 수량을 확인하고 주문 가능 여부를 판단한다.

매도 주문에서는 보유수량과 주문 수량을 확인하고 주문 가능 여부를 판단한다.

주문이 정상적으로 접수되면 주문 데이터를 생성하고 체결 결과에 따라 체결 데이터와 주문 상태를 변경하도록 구현한다.

```text
주문 요청
 ↓
매수 주문
→ 주문가능금액 및 주문 수량 확인

매도 주문
→ 보유수량 및 주문 수량 확인
 ↓
주문 가능 여부 판단
 ↓
주문 생성
 ↓
체결
 ↓
체결 데이터 생성
 ↓
주문 상태 변경
```

프로토타입에서는 기본적인 주문 및 체결 흐름을 구현한다.

동시 주문 규모 확대, Race Condition 재현, Lock 및 기타 동시성 제어 방식 적용은 기본 기능 구현 이후 진행한다.

---

### 3. 주문 매칭

주문이 접수된 이후 상대 주문과 체결되는 기본적인 주문 매칭 과정을 구현한다.

프로젝트의 최종 주문 매칭 범위에서는 지정가 주문, 시장가 주문, 매수·매도 호가, 가격·시간 우선 원칙, 부분 체결 및 미체결 관리를 구현한다.

프로토타입에서는 주문과 체결의 전체 거래 흐름을 연결할 수 있는 기본적인 매칭 기능을 우선 구현한다.

호가창과 가격·시간 우선 원칙, 부분 체결 등의 세부 매칭 기능과 성능 검증은 주문·체결, D+2 결제 및 계좌 기능을 구현한 이후 진행한다.

---

### 4. D+2 결제

주문 체결 결과를 기반으로 결제 예정 데이터를 생성하도록 구현한다.

결제 예정 데이터에서는 계좌, 체결 정보, 매수·매도 구분, 결제 예정 금액, 체결일, 결제 예정일 및 결제 처리 상태를 관리한다.

결제 예정일에 도달한 데이터를 조회하여 결제를 처리하고 결과를 계좌에 반영한 후 결제 상태를 변경하도록 구현한다.

```text
체결
 ↓
결제 예정 데이터 생성
 ↓
결제 예정일 도달
 ↓
결제 대상 조회
 ↓
결제 처리
 ↓
계좌 반영
 ↓
결제 상태 변경
```

프로토타입에서는 정상적인 D+2 결제 흐름을 구현한다.

대량 결제 처리, 처리 중 장애 발생, Retry, 실패 데이터 재처리, 동일 배치 재실행 및 중복 결제 방지는 이후 개선 및 검증 단계에서 진행한다.

---

### 5. 계좌 현황

주문·체결 및 D+2 결제 과정에서 변경되는 사용자 자산 상태를 계좌에 일관되게 반영하도록 구현한다.

계좌에서는 현금, 주문가능금액, 보유종목, 보유수량, 평균매입가, 평가금액, 평가손익, 총자산, D+1 결제 예정 금액 및 D+2 결제 예정 금액을 관리한다.

주문부터 D+2 결제까지 발생하는 상태 변경을 계좌와 연결하도록 구현한다.

```text
주문 발생
 ↓
주문가능금액 및 주문 가능 수량 확인
 ↓
주문 체결
 ↓
보유종목 및 결제 예정 정보 변경
 ↓
D+2 결제
 ↓
결제 결과 계좌 반영
```

각 과정에서 주문 상태, 체결 상태, 보유수량, 주문가능금액, 결제 예정 금액 및 최종 계좌 자산이 일관되게 유지되도록 구현한다.

---

### 6. 회귀 테스트

프로토타입에서 구현한 기능의 입력과 기대 결과를 회귀 테스트로 작성한다.

이후 시스템의 코드와 구조를 변경하더라도 동일한 입력에 대해 기존 비즈니스 결과와 데이터 정합성이 유지되는지 검증한다.

다음 항목을 중심으로 회귀 테스트를 구성한다.

```text
차트 조회
- 종목별 조회
- 기간별 조회

주문
- 정상 매수
- 주문가능금액 부족
- 정상 매도
- 보유수량 부족

체결
- 주문 체결
- 체결 데이터 생성
- 주문 상태 변경

D+2 결제
- 결제 예정 데이터 생성
- 결제 처리
- 결제 상태 변경
- 계좌 반영

계좌
- 주문 이후 상태
- 체결 이후 상태
- D+2 결제 이후 상태

전체 거래 흐름
- 주문 → 체결 → 결제 → 계좌
- 전체 과정의 데이터 정합성
```

시스템을 개선할 때마다 회귀 테스트를 실행하여 기존 기능과 데이터 정합성이 유지되는지 확인한다.

---

### 7. 성능 테스트

프로토타입의 기본 기능 구현과 회귀 테스트를 완료한 이후 최초 성능 테스트를 수행한다.

최적화가 적용되지 않은 Prototype v0의 성능을 측정하여 이후 개선 결과를 비교하기 위한 Baseline으로 사용한다.

다음 지표를 측정한다.

```text
TPS / RPS
평균 응답시간
P95
P99
오류율
데이터 정합성

필요한 경우
- DB 처리시간
- DB Connection 상태
- Lock 경합
- CPU 사용량
- Memory 사용량
```

이후 데이터와 동시 사용자 규모를 확대할 때 동일한 조건과 측정 기준을 사용하여 성능 변화를 비교한다.
