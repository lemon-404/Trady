# 토큰 발급 갱신 폐기 정책 검증

- 작성 날짜: 2026-10-10
- 검증 대상: 같은 앱키의 접근 토큰 발급·재발급·폐기 정책
- 실제 API 검증: 사용자 수동 확인 내용과 자동 테스트 실행 결과를 구분하여 아래 기록

## 1. 확인 목적

같은 앱키를 사용하는 수집 프로세스들이 토큰을 각각 관리할 수 있는지 확인한다. 재발급이 기존 토큰에 미치는 영향과 정상 종료 시 폐기 범위를 확인하여 운영 중 갱신·종료 정책을 결정한다.

## 2. 공식 자료와 확인 경로

| 자료 | 경로 | 확인 내용과 출처 상태 |
|---|---|---|
| 키움 REST API 가이드 | [공식 API 가이드](https://openapi.kiwoom.com/guide/apiguide?dummyVal=0) | 접근토큰 발급 규격을 직접 확인 |
| 키움 게시판의 토큰 안내 | [자주묻는질문 - [키움 REST API] 토큰 만료 기준이 어떻게 될까요?](https://openapi.kiwoom.com/board/Board0301View?dummyVal=0) | 최초 생성후 재요청시 생성시점 6시간 전일경우 기존 접근토큰 전달하며 6시간 후에 재요청시 새로 발급후 전달 후 기존접근토큰은 폐기 |

게시판 경로가 해당 게시글을 계속 직접 가리키는지 확인하고, 가능하면 게시글 제목·게시일·본문을 확인할 수 있는 화면이나 자료도 함께 보관한다.


## 3. 검증 항목과 실제 결과

| 번호 | 확인 항목 | 검증 방법 | 판단 기준 | 결과 근거 |
|---|---|---|---|---|
| 1 | 발급 토큰 사용 | 발급 후 종목정보 조회 | 조회 성공과 미래 만료 시각 | 사용자 수동 확인. 자동 테스트 작성, 실제 실행 전 |
| 2 | 짧은 간격 재요청 | 발급 API를 두 번 호출하고 토큰·만료 시각 비교 | 토큰 동일, 만료 시각 유지 | Postman에서 동일 토큰 반환 확인. 만료 시각 비교는 자동 테스트 실행 시 확인 |
| 3 | 6시간 이후 재요청 | 공식 안내를 설계 근거로 사용 | 새 토큰 발급 및 기존 토큰 폐기 | 공식 안내 기준. 실제 요청 테스트 제외 |
| 4 | 재발급 후 이전 토큰 | 공식 안내의 기존 토큰 폐기 정책 적용 | 이전 토큰은 유효하게 사용할 수 없음 | 공식 안내 기준. 실제 요청 테스트 제외 |
| 5 | 명시적 폐기 | 조회 성공 → 폐기 → 같은 토큰으로 다시 조회 | 폐기 성공 후 인증 거절 | 자동 테스트 작성, 실제 실행 전 |
| 6 | 복수 토큰 간 폐기 영향 | 공식 안내상 독립적인 복수 토큰을 유지하는 실험 제외 | 같은 앱키로 발급 요청해도 독립 토큰이라고 가정하지 않음 | 안내에 따라 검증 범위에서 제외 |
| 7 | 자연 만료 | 사전에 보관한 토큰의 실제 만료 시각 이후 조회 | 만료 시각 경과 및 인증 거절 | 별도 실행 테스트 작성, 자연 만료 토큰 필요 |


## 4. 테스트 실행 방법

테스트 위치는 main 코드와 같은 패키지의 src/test/java다. Auth Client, Stock Client와 WebClient 설정을 등록하며 Lifecycle·Provider·DB는 등록하지 않는다. Provider를 거치면 보관 토큰을 반환하여 실제 재발급 요청이 발생하지 않을 수 있기 때문이다.

### 1·2·5번: 발급·재요청·폐기

- 설정 파일에 기존 키움 인증 설정이 필요하다.
- 환경변수 KIWOOM_AUTH_LIVE_TEST=true로 명시적으로 활성화한다.
- KIWOOM_EXPIRY_LIVE_TEST는 설정하지 않거나 false로 둔다.
- backend에서 Gradle의 test 작업에 --tests trady.com.backend.global.dataloader.kiwoom.auth.KiwoomTokenPolicyLiveTest를 지정하거나 IDE에서 해당 클래스를 실행한다.
- 각 테스트는 실제 발급·조회 요청을 보내며 테스트 종료 시 현재 토큰을 폐기한다. 같은 앱키를 사용하는 다른 수집 프로세스가 없는 전용 실험 환경에서 실행한다.
- 토큰 원문을 출력하거나 실패 메시지에 포함하지 않고 동일 여부만 검증한다.
- 연속 두 요청의 동일 여부를 확인하는 테스트이며, 6시간 전체 구간을 시간 경과로 검증하는 테스트는 아니다.

### 7번: 자연 만료

- 이전에 유효한 상태로 사용한 토큰과 응답의 expires_dt를 별도로 보관한다. 문서나 Git에 토큰 값을 저장하지 않는다.
- 그 토큰을 명시적으로 폐기하거나 발급 후 6시간 이후 재발급하여 무효화하지 않고 실제 만료까지 둔다.
- KIWOOM_AUTH_LIVE_TEST=true와 KIWOOM_EXPIRY_LIVE_TEST=true를 설정한다.
- KIWOOM_EXPIRED_TOKEN에 보관한 토큰, KIWOOM_EXPIRED_TOKEN_EXPIRES_DT에 실제 만료 시각(yyyyMMddHHmmss)을 설정한다.
- 이 모드에서는 1·2·5번이 자동으로 제외된다. 다른 발급·폐기 요청이 실험에 개입하지 않도록 한다.
- 테스트는 실제 만료 시각이 지났는지 확인하고 종목 조회가 인증 거절되는지 검증한다. 발급·폐기를 호출하거나 24시간 동안 기다리는 테스트가 아니다.
- 토큰의 사전 유효성과 미폐기·미교체 조건은 실험자가 보장해야 한다. 그렇지 않으면 거절 응답만으로 자연 만료가 원인이라고 판단할 수 없다.
- 환경변수 입력이 없으면 7번은 건너뛴다. 로컬 Clock 변경으로 키움 서버의 만료 정책을 확인하지 않는다.

요청 제한·통신 장애·일반 업무 오류를 인증 거절로 간주하지 않는다. 실제 응답이 예상한 인증 오류 형태와 다르면 오류 코드를 확인하여 테스트의 판단 기준을 보완한다.

## 5. 실험 결과와 설계 결정

각 실험의 관찰과 그에 따른 설계 판단을 같은 표로 연결한다. 실제 자동 테스트를 실행한 뒤 환경·시간과 확인한 항목을 갱신한다.

### 1. 발급 토큰의 사용

| 구분 | 내용 |
|---|---|
| 실험 결과 | 사용자가 발급 토큰으로 실제 사용을 확인함. 자동 테스트의 종목 조회와 만료 시각 확인은 실행 전 |
| 요청 조건 | 사용자 수동 실험의 환경·시각은 미기록 |
| 설계 결정 | Auth Client의 발급 결과를 검증한 뒤 토큰 제공에 사용 |
| 추가 확인 | 자동 테스트에서 종목 응답 성공과 만료 시각 확인 |

### 2. 짧은 간격 재요청

| 구분 | 내용 |
|---|---|
| 실험 결과 | 사용자 Postman 실험에서 연속 발급 요청에 동일한 토큰이 반환됨 |
| 요청 조건 | 같은 앱키, 사용자가 확인한 6시간 이내 요청. 정확한 최초 생성 시각·환경은 미기록 |
| 설계 결정 | 발급 요청별로 독립적인 토큰이 생긴다고 가정하지 않음. 프로세스별 토큰 폐기가 다른 사용자에게 영향을 줄 수 있어 관리 주체를 조율 |
| 추가 확인 | 만료 시각 유지 여부는 자동 테스트에서 비교. 6시간 이후의 교체·폐기는 공식 안내를 근거로 삼음 |

### 5. 명시적 폐기

| 구분 | 내용 |
|---|---|
| 실험 결과 | 자동 테스트 실행 전 |
| 요청 조건 | 폐기 전 동일 종목 조회 성공을 먼저 확인하고, 폐기 후 같은 토큰으로 다시 조회 |
| 설계 결정 기준 | 인증 거절이 확인되면 정상 종료용 폐기 이후 해당 토큰을 제공하지 않도록 관리 |
| 추가 확인 | 원격 폐기 응답과 폐기 후 조회의 인증 거절을 함께 확인 |

### 7. 자연 만료

| 구분 | 내용 |
|---|---|
| 실험 결과 | 자동 테스트 실행 전 |
| 요청 조건 | 사전에 유효했던 토큰을 재발급·폐기 없이 보관하고 실제 만료 이후 조회 |
| 설계 결정 기준 | 자연 만료가 확인되면 외부 요청 전 만료 여부를 판단하여 필요 시 갱신. 정상 종료용 폐기와 운영 중 갱신은 별도 동작으로 관리 |
| 추가 확인 | 응답 만료 시각, 미폐기·미교체 조건 및 실제 인증 거절 확인 |

### 공식 재발급 정책에 따른 결정

| 근거 | 설계에 적용할 내용 |
|---|---|
| 6시간 이후 재발급 시 이전 토큰 자동 폐기 안내 | 갱신 과정에서 이전 토큰을 추가로 폐기하는 동작을 바로 넣지 않음 |
| 같은 앱키의 기존 토큰 반환 또는 교체 정책 | 서로 다른 프로세스가 독립적으로 발급·폐기해도 안전하다고 가정하지 않음 |

호출 제한 적용 단위와 여러 토큰으로 요청 예산이 늘어나는지는 별도의 종목·차트 API 검증에서 다룬다.
