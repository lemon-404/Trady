# commit-message — 커밋 메시지 작성

아래 규칙으로 커밋 메시지를 작성한다. 

## 메시지 형식

```text
type: Subject

본문
```

## Type 종류

| Type | 사용 기준 |
|---|---|
| ADD | 새로운 코드나 파일 추가 |
| MODIFY | 기존 기능 수정 |
| FIX | 버그 수정 |
| DOCS | 문서·주석·README 등 수정 |
| REMOVE | 코드나 파일 삭제 |
| IMPLEMENT | ADD보다 큰 단위로 전체 동작 구현 |
| TEST | 테스트 코드 추가 및 수정 |
| RENAME | 파일명·변수명·함수명 등 이름 변경 |
| MOVE | 코드나 파일 이동 |
| CHORE | 빌드·패키지 매니저 설정 등 기타 작업 |

## 변경 범위 확인

- 사용자 지정 변경 목록·파일·Task 우선
- staging 여부와 관계없이 아래 세 명령 모두 확인
- `git status --short`: 전체 변경 목록과 미추적 파일 확인
- `git diff`: staging하지 않은 수정 확인
- `git diff --cached`: staging한 수정 확인


## 작성 규칙

### 제목(Subject) 작성 규칙

- 제목 작성 후 반드시 한 줄 띄워서 본문과 구분
- 제목은 대문자로 시작, 마침표는 쓰지 않음
- 제목은 명령문으로 작성

### 본문(Body) 작성 규칙

- 본문 작성 후 한 줄 띄워서 Resolves 영역과 구분
- 각 행은 72자 이내로 작성
- "무엇을", "왜" 했는지를 중심으로 작성
- 본문은 여러 줄로 구성 가능

## 최종 검증

- 복사 가능한 `text` 코드 블록으로 메시지를 제공한다. 작성 규칙의 안내 문구나 주석은 포함하지 않는다.
- 제목 형식과 타입, 제목·본문 구분, 본문 행 길이, 실제 변경 범위와 표현의 일치를 확인한다.

## 주의사항

- 일반 diff에 나오지 않는 관련 미추적 파일은 내용 직접 확인
- staged 변경만 요청한 경우 unstaged·미추적 변경 제외
- 범위 미지정 시 세 명령 결과와 관련 신규 파일 종합
- Git 조회 차단 시 확인 가능한 파일·사용자 설명 활용 및 확인 한계 명시
- 이전 대화만으로 현재 변경·테스트 성공 단정 금지
- 조회 목적의 `git add`, 파일·staging 상태 변경, Git 설정 변경 금지
- 메시지 작성 요청만으로 `git add`, `git commit`, `git push` 실행 및 파일 수정 금지
- 메시지 파일 저장·커밋 실행은 해당 요청 범위와 기존 권한에 따라 수행
