# work-plan — 사용자용 작업 계획

사용자가 무엇을 왜 구현하려는지, 어떤 구조와 순서로 구현할지 이해할 수 있도록 한국어 작업 계획을 작성한다. 이후 개선 작업에서도 당시의 구현 목적과 설계 근거를 확인할 수 있도록 설명한다. [작업 계획 템플릿](assets/work-plan-template.md)의 작성기준을 따라 내용을 채운다.

## 저장 규칙

- 프로젝트 루트 기준 `docs/work-plan/backend/yyyy-mm-dd 작업 제목.md` 또는 `docs/work-plan/frontend/yyyy-mm-dd 작업 제목.md`에 저장한다.
- 날짜는 사용자가 지정한 작업 날짜를 우선하고, 지정하지 않았다면 사용자 현지 날짜를 사용한다.
- 파일명은 날짜 뒤 공백과 사람이 읽을 수 있는 작업 제목으로 구성한다. 예: `2026-10-10 주가 정보 동기화와 차트 조회.md`.
- 기존 작업 계획의 수정 요청이면 해당 파일을 먼저 읽고 요청 범위에 해당하는 내용을 수정한다. 기존 목적과 설계 근거는 변경이 필요한 부분을 제외하고 보존한다.
- 양쪽 영역에 걸친 작업은 주된 작업 영역에 작성하고 관련 영역을 링크한다. 영역별 계획을 요청받으면 나누어 작성한다.
- `docs/superpowers/plans/`의 에이전트 실행용 구현 계획과 구분한다. 관련 구현 계획은 링크로 연결하며 사용자용 작업 계획을 그 경로에 저장하지 않는다.

## 작성 방식

1. 사용자 요구사항, 관련 구현 계획, 기존 코드와 설계 문서를 확인하여 작업 목적과 변경 대상을 파악한다.
2. 템플릿의 8개 목차와 순서를 유지하고, 각 목차의 작성기준을 따른다. 해당하지 않는 항목은 해당 없음으로 표시하고 이유를 짧게 적는다.
3. 작업 목적, 설계 의도, 동작 구조와 구현 순서를 정의한다. 구현 과정에서 설계가 변경되면 사용자 검토 후 변경 이유와 함께 계획에 반영한다. 수행 이력이나 실행 결과를 추가하는 방식으로 갱신하지 않는다.
4. 참고 자료는 공식 자료의 이름, URL, 사용 목적을 표로 정리한다. 확인하지 않은 링크를 만들어내지 않는다.
5. 생성·수정할 파일은 프로젝트 루트 기준의 전체 상대 경로, 역할, 변경 유형과 관련 Task를 작성한다. 공통 경로를 생략하거나 기준 경로를 혼용하지 않는다.
6. 단계는 Task 1부터 선행 관계에 따라 작성하고, 각 단계의 목적과 구현할 내용을 정의한다.
7. 검증 기준은 확인할 동작, 검증 방법·환경, 기대 결과로 구성한다. 실제 실행 결과, 통과·실패 여부, 문제 처리 이력은 포함하지 않는다.
8. 후속 개선 과제는 이번 범위에서 제외한 기능과 향후 개선 요소만 `- [ ]` 체크박스로 작성한다. 현재 계획의 미구현 Task나 미실행 테스트를 옮겨 적거나 완료 여부를 추적하지 않는다. 후속 개선 과제가 없으면 없다고 적는다.

## 내용 범위 및 최종 확인

- 구현할 내용은 목적과 설계 이유를 설명하고 관련 파일을 연결한다. 사용자가 코드 예시를 요청하면 그 요청을 따른다.
- API 키, 시크릿, 토큰 및 민감한 원문 응답을 문서에 포함하지 않는다.
- 템플릿의 {{...}} 부분은 해당 작업의 계획으로 채운다. 아직 정하지 않은 값이나 정책은 결정에 필요한 확인 방법을 적고 임의로 확정하지 않는다.
- 기존 구현과 계획이 다르면 예정된 변경인지 설계 변경에 따른 불일치인지 구분한다. 계획 수정이 필요하면 차이를 사용자에게 알리고 검토 후 반영한다. 계획에 맞추기 위해 구현이나 기존 설계 문서를 임의로 변경하지 않는다.
- 저장 경로와 파일명, 8개 목차, 링크를 확인하고 작업 목표·범위·구조·Task·검증 기준이 서로 일치하는지 검토한다. 후속 개선 과제가 이번 작업 범위와 구분되는지도 확인한다.
- 템플릿에 정의된 항목만 작성한다. 템플릿의 작성기준 문장은 실제 작업 계획에서 제거한다. 문서의 목적·작성 시점·수정 절차 등 작성 지침을 설명하는 서문이나 안내 문구를 임의로 추가하지 않는다.
- 수행 상태, 수행 결과 및 근거, 실제 검증 결과, 완료 범위 요약 등 결과 보고 항목은 작성하지 않는다.
