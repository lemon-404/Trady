# work-record — 작업 수행 기록

작업 계획의 Task별로 무엇을 확인했고, 그 결과로 어떤 결정을 내렸는지 한국어로 기록한다.

## 저장 규칙

- 관련 work-plan을 먼저 읽고 기록이 속하는 Task 번호와 제목을 확인한다. 기록은 Task별로 작성하고 서로 다른 Task의 수행 내용을 한 문서에 합치지 않는다. 계획이나 관련 Task가 불명확하면 임의로 연결하지 않고 사용자에게 확인받고 기록한다.
- work-plan은 기존 위치에 유지한다. 계획 파일의 확장자를 뺀 이름으로 같은 위치에 폴더를 만들고 그 안에 수행 기록을 저장한다.
- 계획 날짜와 작업명은 그대로 사용한다. 수행 기록 파일명은 `Task {번호}. {기록 주제}.md`로 작성하며, 번호는 work-plan의 Task 번호와 일치시킨다.
- 같은 Task에서 검증·실험·분석 주제가 나뉘면 동일한 Task 번호를 붙인 여러 기록으로 작성할 수 있다.
- 문서 상단에 `관련 Task: Task {번호}. {work-plan의 Task 제목}`을 적는다.
- 기존 기록의 수정 요청이면 해당 파일을 갱신한다. 다른 문서를 일괄 이동하거나 이름을 변경하지 않는다.

예:

~~~text
docs/work-plan/backend/
├─ 2026-10-10 키움 API 토큰 관리 구조.md
└─ 2026-10-10 키움 API 토큰 관리 구조/
   └─ Task 1. 토큰 발급 갱신 폐기 정책 검증.md
~~~

프론트엔드 작업은 동일한 규칙을 `docs/work-plan/frontend/`에 적용한다. 기록의 작성 날짜는 문서 안에 적고 작업 계획 날짜와 구분한다.

## 작성 방식

1. 관련 계획의 해당 Task, 기존 기록, 코드·실행 설정과 실제 결과 근거를 확인한다. 사용자가 직접 확인한 내용과 실행 기록에서 확인한 내용을 구분한다.
2. 검증·실험 기록은 [검증 기록 템플릿](assets/work-record-template.md)을 읽고 작성한다. 실행 테스트가 없는 분석 기록은 같은 원칙으로 목적·자료·확인 방법·실제 관찰을 정리하고 해당하지 않는 테스트 안내를 생략한다.
3. 확인 목적, 참고 자료, 테스트 방법, 검증 결과 순으로 작성한다. 참고 자료에는 실제 참고한 공식 자료와 관련 work-plan 문서를 링크한다. 별도 참고 자료 섹션이나 결과 요약표를 덧붙여 같은 내용을 반복하지 않는다.
4. 테스트 방법에는 코드 경로, 필요한 때 개별 메서드로 실행하는 방법, 필요한 실행 설정과 주의 사항을 모은다. 태그 제외·환경변수·병렬 실행 등은 현재 코드와 설정을 확인해 기록하며 특정 테스트의 설정을 모든 테스트의 규칙으로 고정하지 않는다.
5. 검증 결과는 `### 1. 항목명`부터 항목별로 한 번씩 작성한다. 각 표에는 `검증 방법`, `예상 결과`, `실제 결과` 세 행만 넣는다. 관련 메서드는 검증 방법에 함께 적을 수 있다. 실행 조건·시각이 결과 해석에 필요한 경우 해당 방법 또는 결과에 포함한다.
6. 표 아래에는 확인한 결과를 근거로 내린 결정과 이유, 또는 확인하지 못한 부분과 다음 조치를 문장으로 적는다. 결정을 억지로 붙이지 않으며 실행 참고·설계 결정·판정 행을 표에 추가하지 않는다.
7. 작성 지침과 템플릿의 자리표시자는 실제 문서에서 제거한다. 사용자가 정한 양식과 표현을 우선한다.

## 결과와 재검증 이력

- 실제 실행이나 사용자 확인 근거가 없는 성공·실패를 만들어내지 않는다. 실험하지 않은 항목의 실제 결과는 `실험 미수행`으로 적는다.
- 공식 안내를 근거로 내린 결정은 표 아래에서 공식 안내에 따른 것임을 밝힌다. 실험 결과로 확인했다고 표현하지 않는다.
- 테스트를 변경하여 재검증하면 같은 항목 아래에 `#### v1`, `#### v2`를 둔다. 각 버전에 같은 세 행의 표를 사용하고 이전 관찰은 보존한다. 한 번의 검증은 버전 제목 없이 기록해도 된다.
- 새 버전의 표 아래에는 이전 버전의 문제, 적용한 변경, 이번에 확인한 결과를 연결해 설명한다. 테스트 변경 없이 같은 테스트를 다시 실행한 것만으로 버전을 늘리지 않는다.
- 변경된 테스트가 아직 없다면 다음 조치만 적는다. 실행하지 않은 v2를 성공한 기록처럼 작성하지 않는다.
- 구현 조건을 그대로 옮기기보다 확인 의미가 드러나게 쓴다. 예: '만료 시각이 현재보다 이후인지 확인' 대신 '발급된 토큰의 유효기간이 남아 있는지 확인'.

## 최종 확인

- 관련 계획의 위치를 유지했는지, 수행 기록 폴더가 계획 파일명과 일치하는지 확인한다.
- 파일명이 `Task {번호}. {기록 주제}.md` 형식인지, 문서 상단의 Task 번호·제목이 work-plan과 일치하는지, 기록이 해당 Task 범위로 작성되었는지 확인한다.
- 각 검증 항목이 한 번씩 나타나는지, 표가 세 행으로 구성되는지, 결정·다음 조치가 표 밖에 있는지 검토한다.
- 기대와 실제 관찰, 공식 안내와 실험 결과, 미수행과 실행 중 확인 불가를 구분한다.
- 상대 링크는 문서 위치 기준으로 작성한다. 문서를 이동한 경우 이동에 따른 내부 링크와 해당 문서를 가리키는 참조 경로를 함께 확인한다.
- API 키·시크릿·접근 토큰 등 인증정보를 기록하지 않는다. 재현 가능한 조건과 결과를 남긴다.
- 수행 기록을 작성하는 것만으로 계획 문서·설계·코드 변경이나 외부 API 실험이 승인된 것으로 해석하지 않는다.
