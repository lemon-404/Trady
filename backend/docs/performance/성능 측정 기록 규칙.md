# 성능 측정 기록 규칙

같은 조회 기능의 성능 개선 전후를 비교할 수 있도록 측정 결과의 저장 위치, 파일명과 JSON 형식을 정한다.

## 1. 폴더 구조

~~~text
backend/docs/performance/
├─ 성능 측정 기록 규칙.md
└─ candle-query/
   ├─ 1. 단일 조회/
   │  └─ RepoV1-ServiceV1-20261014-153000.json
   └─ 2. 기간 연속 조회/
      └─ RepoV1-ServiceV1-20261014-153000.json
~~~

리소스별로 폴더를 나누고 그 아래에 측정 방식별 결과를 저장한다. 캔들 조회는 candle-query를 사용한다.

| 폴더 | 목적 |
|---|---|
| 1. 단일 조회 | 같은 조회 조건을 반복 호출한 결과 |
| 2. 기간 연속 조회 | 지정 기간을 커서로 연속 탐색한 페이지별 결과 |

## 2. 파일명과 버전

파일명은 Repo{버전}-Service{버전}-{yyyyMMdd}-{HHmmss}.json 형식으로 작성한다. 시각은 Asia/Seoul 기준이며 한 실행의 단일·기간 조회 결과는 같은 실행 시각을 사용한다. 같은 버전을 다시 측정하면 새로운 시각으로 저장하여 기존 결과를 보존한다. 동시에 실행해 파일명이 겹치면 밀리초를 추가한다.

Repository와 Service 버전은 각각 기록한다. 예를 들어 CandleQueryRepositoryV1과 CandleQueryServiceV2를 사용하면 RepoV1-ServiceV2를 파일명에 사용한다. 같은 기능이라도 버전 조합이 다르면 별도 결과로 보관한다.

## 3. 공통 기록 항목

| JSON 필드 | 내용 |
|---|---|
| repositoryVersion | 실제 측정에 사용한 Repository 클래스명과 버전 |
| serviceVersion | 실제 측정에 사용한 Service 클래스명과 버전 |
| measuredAt | 시간대 오프셋을 포함한 측정 시작 시각 |
| measurementScope | Service 호출을 측정할 때 service |
| stockCode | 측정 대상 종목 코드 |
| interval | 봉 주기: 1·5·15 |
| pageSize | 실제 Service에 적용한 페이지 크기 |
| warmupCount | 통계에서 제외한 사전 호출 횟수 |
| statistics | 측정 시간의 합계·평균·중앙값·최댓값 |

한 JSON 파일에는 실행 한 번의 결과를 담고 results 배열에서 봉 주기별 결과를 구분한다. 각 봉 주기의 종목 코드와 페이지 크기를 명시한다. 현재 페이지 크기 초안은 1분봉 390개, 5분봉 78개, 15분봉 26개이며 변경 시 실제 적용한 값을 기록한다.

## 4. 단일 조회

같은 종목·봉 주기·기준 시각으로 최초 조회를 반복한다.

| JSON 필드 | 내용 |
|---|---|
| cursor | 반복 조회에 사용한 기준 시각 |
| measurementCount | 워밍업을 제외한 측정 호출 횟수 |
| requests | 호출 순번·시간·반환 개수 |
| requests[].sequence | 측정 호출 순번 |
| requests[].elapsedMs | 해당 호출의 처리 시간, 밀리초 |
| requests[].returnedCount | 응답 캔들 개수 |

아래 값은 형식 설명용 예시이며 실제 측정 결과가 아니다.

~~~json
{
  "repositoryVersion": "CandleQueryRepositoryV1",
  "serviceVersion": "CandleQueryServiceV1",
  "measuredAt": "2026-10-14T15:30:00+09:00",
  "measurementScope": "service",
  "results": [
    {
      "stockCode": "005930",
      "interval": "1",
      "pageSize": 390,
      "cursor": "2026-10-09T23:59:59",
      "warmupCount": 3,
      "measurementCount": 2,
      "requests": [
        {"sequence": 1, "elapsedMs": 10.0, "returnedCount": 390},
        {"sequence": 2, "elapsedMs": 14.0, "returnedCount": 390}
      ],
      "statistics": {
        "totalMs": 24.0,
        "averageMs": 12.0,
        "medianMs": 12.0,
        "maxMs": 14.0
      }
    }
  ]
}
~~~

현재 단일 조회 테스트의 반복 측정 횟수는 워밍업 3회를 제외한 10회다. 예시는 길이를 줄이기 위해 2회만 표시했다.

## 5. 기간 연속 조회

상한 시각에서 최초 페이지를 조회하고 응답 커서로 더 과거의 페이지를 반복 조회한다.

| JSON 필드 | 내용 |
|---|---|
| rangeStart | 조회 기간의 하한 시각, 포함 |
| rangeEnd | 조회 기간의 상한 시각, 포함 |
| pageCount | 최초 조회를 포함한 실제 측정 페이지 호출 수 |
| pages | 페이지별 요청 커서·시간·반환 개수 |
| pages[].page | 페이지 순번 |
| pages[].requestType | initial 또는 continuous |
| pages[].cursor | 해당 페이지 요청의 기준 시각 |
| pages[].elapsedMs | 해당 호출의 처리 시간, 밀리초 |
| pages[].returnedCount | 해당 응답의 전체 캔들 개수 |
| pages[].inRangeCount | 해당 응답 중 지정 기간 안의 캔들 개수 |
| pages[].oldestTime | 해당 페이지의 가장 오래된 시각. 빈 응답은 null |
| pages[].newestTime | 해당 페이지의 가장 최근 시각. 빈 응답은 null |
| pages[].nextCursor | 응답에 포함된 다음 커서 |
| pages[].contYn | 응답의 연속 조회 가능 여부 |
| totalInRangeCount | 모든 페이지에서 조회한 기간 내 캔들 개수의 합계 |
| stopReason | range-start-reached 또는 data-exhausted |

현재 조회 기간은 2025-10-08 00:00:00부터 2026-10-09 23:59:59까지다. 상한에서 과거 방향으로 이동한다. 하한에 도달하거나 추가 데이터가 없으면 종료한다. 데이터가 먼저 소진된 결과를 전체 기간의 데이터가 존재한다는 의미로 해석하지 않는다.

하한을 넘는 페이지도 전체 Service 호출 시간을 측정한다. 반환 개수는 실제 응답 전체 개수를 기록하고, 지정 기간 내 개수는 inRangeCount로 따로 기록한다. 기간 내 데이터가 모두 반환된 마지막 페이지에서는 과거 데이터가 더 있어도 범위 탐색을 종료할 수 있다.

단일 조회의 measurementCount는 동일 조건의 반복 호출 횟수이고, 기간 조회의 pageCount는 커서로 이동하며 호출한 페이지 수다. 워밍업은 두 값에서 제외한다.

## 6. 측정과 통계 기준

Service 호출 직전에 System.nanoTime()을 기록하고 호출 반환 직후 차이를 밀리초로 환산한다. 검증, 콘솔 출력과 JSON 파일 저장은 측정 구간 밖에서 수행한다.

- totalMs: 측정 호출 시간의 합계
- averageMs: totalMs를 측정 호출 수로 나눈 값
- medianMs: 시간을 정렬한 중앙값. 짝수이면 가운데 두 값의 평균
- maxMs: 가장 오래 걸린 호출의 시간

기간 조회의 전체 통계에는 최초·연속 페이지를 모두 포함한다. totalMs는 호출 시간 합계이며, 로그 출력·검증·파일 저장을 포함한 테스트 전체 실행 시간은 아니다. 빈 응답을 반환한 호출도 실제 측정했다면 페이지 수와 통계에 포함한다.

Service 측정 범위에는 트랜잭션·DB 조회·엔티티 로딩·응답 DTO 구성이 포함된다. HTTP 통신과 JSON 직렬화 시간은 포함하지 않는다. PostgreSQL 실행 계획에서 확인하는 SQL 실행 시간과도 구분한다.

## 7. 비교 기준

같은 종목·봉 주기·기준 시각·기간·페이지 크기·워밍업 방식과 측정 횟수로 비교한다. 적재 데이터와 DB 실행 환경도 같게 유지한다. 반환 개수나 탐색 페이지 수가 달라졌다면 단순히 합계 시간만으로 개선 여부를 판단하지 않는다.

워밍업과 반복 호출은 DB 캐시에 영향을 주므로 결과를 항상 최초 디스크 읽기 성능으로 해석하지 않는다. 같은 조건의 여러 실행 결과를 함께 비교한다. 측정 실패를 정상 완료 결과처럼 기록하지 않으며, 실패 내역을 남길 때는 성공한 호출 결과와 종료 원인을 명시한다.
