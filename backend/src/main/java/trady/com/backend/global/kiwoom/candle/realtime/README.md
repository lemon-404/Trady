# REST 기반 차트 수집 설계

## 1. 차트 수집 알고리즘

### 배경: 수집 대상과 API 요청량

수집 대상은 1·5·15·30·60분봉과 일·주·월·년봉이다. 현재 설계에서는 동일 인증 주체의 TR별 초당 5회를 호출 예산으로 사용한다.

| 봉 주기 | TR | 종목당 1회 갱신 요청량 | 50종목 요청량 | 10종목 요청량 |
|---|---|---:|---:|---:|
| 1분봉 | ka10080 | 1회 | 50회 | 10회 |
| 5분봉 | ka10080 | 1회 | 50회 | 10회 |
| 15분봉 | ka10080 | 1회 | 50회 | 10회 |
| 30분봉 | ka10080 | 1회 | 50회 | 10회 |
| 60분봉 | ka10080 | 1회 | 50회 | 10회 |
| 일봉 | ka10081 | 1회 | 50회 | 10회 |
| 주봉 | ka10082 | 1회 | 50회 | 10회 |
| 월봉 | ka10083 | 1회 | 50회 | 10회 |
| 년봉 | ka10094 | 1회 | 50회 | 10회 |
| 합계 | | 9회 | 450회 | 90회 |

다섯 분봉은 모두 ka10080의 호출 예산을 공유한다.

| 종목 수 | 전체 분봉 요청량 | 전체 분봉 순회 이론상 최소 시간 |
|---:|---:|---:|
| 50종목 | 250회 | 50초 |
| 10종목 | 50회 | 10초 |

위 시간은 오류·응답 지연 없이 호출 예산을 모두 사용하는 경우다. 일정한 시간만큼 과거 시장을 재생하는 고정 지연 방식은 아니다.

### 문제: 동일 주기 조회의 한계

모든 봉을 같은 빈도로 조회하면 짧은 주기의 최신성을 확보하기 어렵다. 특히 1분봉의 갱신이 늦어지면 사용자가 현재 시장의 움직임을 파악하기 어렵다.

반대로 완성 봉만 표시하면 긴 주기에서 현재 진행 구간이 보이지 않는다. 따라서 진행 봉도 주기적으로 갱신하되, 짧은 봉에 요청 예산을 우선 배정한다.

### 선택: 10종목과 봉별 우선순위

수집 대상을 10종목으로 축소하고, 다음을 초기 갱신 목표로 설정한다.

| 봉 주기 | 10종목 전체 갱신 목표 간격 | 평균 요청량 |
|---|---:|---:|
| 1분봉 | 4초 | 2.50회/초 |
| 5분봉 | 12초 | 0.83회/초 |
| 15분봉 | 24초 | 0.42회/초 |
| 30분봉 | 36초 | 0.28회/초 |
| 60분봉 | 60초 | 0.17회/초 |
| 분봉 합계 | | 약 4.19회/초 |

실제 요청은 연속된 1초 구간에서 최대 5회로 제한한다. 남은 예산은 경계 보정이나 지연된 작업 처리에 여유로 사용한다.

일·주·월·년봉은 각각 별도 TR 예산으로 관리하며, 긴 주기일수록 갱신 빈도를 낮춘다. 구체적인 간격은 별도 설정으로 정한다.

### 결과: 수집과 저장 방식

```text
매초 스케줄 실행
    → 봉별 갱신 목표와 대기 시간을 기준으로 작업 선택
    → 해당 주기의 종목 큐에서 다음 종목 선택
    → 처리 중 여부와 TR 호출 예산 확인
    → REST 비동기 요청
    → 진행 봉 갱신 + 종료된 봉·누락 봉 보정
```

- 주기별 종목 큐를 순환하여 특정 종목이 반복적으로 밀리는 것을 방지한다.
- 같은 종목·주기는 이전 저장이 끝난 후 다음 요청을 실행한다.
- 진행 봉은 조회 당시의 OHLCV로 교체한다.
- 한 응답에서 마지막 반영 시각 이후의 완료 봉과 경계 보정 대상도 함께 저장한다.
- 오류는 기록 후 폐기하며 재시도하지 않는다.
- 수집하지 못한 봉 내부의 움직임을 임의로 복원하지 않는다.

## 2. 실시간 체결과 차트의 관계

### 배경과 문제

사용자는 차트를 보고 주문을 판단하지만, 체결은 현재 시장의 호가와 체결 이벤트를 기준으로 처리된다.

차트가 하루·1시간·10분 전 상태라면 사용자가 판단한 가격과 현재 주문 가능한 가격 사이에 차이가 커질 수 있다. 이는 사용자에게 부자연스러운 체결로 느껴질 수 있다.

### 선택 및 결과

| 기능 | 데이터 기준 |
|---|---|
| 주문 체결 판단 | 실시간 WS 체결·호가 이벤트 |
| 현재가·호가창 | 실시간 WS 데이터 |
| 차트 | 봉별 우선순위에 따른 REST 갱신 |

체결 시스템은 실시간으로 유지하고, 사용자의 단기 판단에 영향을 주는 1분봉을 가장 자주 갱신한다. 이를 통해 차트와 현재 시장의 시점 차이를 줄인다.

현재가·호가창과 차트의 마지막 반영 시각을 함께 표시하여, 차트가 갱신되기 전에도 현재 주문 가능한 가격을 확인할 수 있도록 한다.

## 3. 적용 범위와 남은 한계

이번 방법은 실시간 체결과 주기적 차트 갱신을 결합하는 방식이다.

10종목과 봉 우선순위로 사용자 경험의 부자연스러움을 완화하되, 급변 구간에서는 수초 사이에도 차트와 체결 가격이 달라질 수 있다. 실제 갱신 간격은 API 응답 시간과 요청·저장 작업의 처리 상태에 따라 달라질 수 있다.
